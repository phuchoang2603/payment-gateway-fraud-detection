# GitOps deployment

GitOps manages the prod-only Kubeflow workspace and the minimum payment gateway. [talos-proxmox](https://github.com/phuchoang2603/talos-proxmox/blob/main/docs/operations/kubeflow.md) owns the shared Talos clusters, Argo CD, Kubeflow controllers, Dex SSO, External Secrets, Argo Workflows, and ingress. This repository owns its Profile, gateway workloads and service policies.

The Argo root is [`infra/argocd/prod/root.yaml`](../../infra/argocd/prod/root.yaml). Its children target the prod cluster. Gateway workloads use `payment-gateway`; Profile resources use `argo-cd` as their Argo destination so Argo does not create the Profile-owned `fraud-ml-prod` namespace first.

| Environment | Root                        | Enabled child Application                   | Helm release         | Configuration                                       |
| ----------- | --------------------------- | ------------------------------------------- | -------------------- | --------------------------------------------------- |
| Prod        | `payment-gateway-prod-root` | `payment-gateway-prod-secret-store`         | `secret-store`       | `values-prod.yaml`: shared Doppler `prd` ClusterSecretStore, token in `operators` |
| Prod        | `payment-gateway-prod-root` | `payment-gateway-prod-kubeflow-workspace`   | `kubeflow-workspace` | Profile and namespace resources in `fraud-ml-prod`  |

Gateway and feature children are `payment-gateway-prod-{payment-gateway,kafka,fraud-features}` in the `payment-gateway` namespace. The `infra/charts/payment-gateway` application chart owns all six Go services, including fraud, through one `services` map plus the gateway database, idempotency and authorization Redis resources, secrets, routing and policies. The independent `infra/charts/fraud-features` chart owns Flink, the Feast writer/server and Feast Redis; the platform owns the Flink operator in `operators`. The chart declares five CNPG databases with separate roles; Payments and Fraud use owner roles for migrations and restricted `payments_app` / `fraud_app` runtime roles. Payments has a separate replication principal restricted to the event ledger. Three operator-managed Redis resources isolate idempotency, authorization observations and Feast, each with independent credentials, clients, memory limits and noeviction. Gateway `features.enabled` defaults to false and is enabled in production for shadow Fraud retrieval through `features.url`; rules remain authoritative and authorization counters remain observe-only. Full replay, resource and outage acceptance remain pending. The feature chart independently controls `feast.enabled` and `streaming.enabled`, both true by default; enabling Feast adds its SDK writer, official server and Redis. Both charts must use the same epoch and definition hash. The writer runs one replica with Recreate upgrades; no offline writer may target its active keys. Its registry is reconstructed from code in ephemeral memory. The feature journal is `fraud.feature-updates.v1.live-v1`; replay uses a separate topic and epoch. Kafka/Connect publish ledger bytes to the internal `payments.events.v1` topic. Only Edge `/checkout/*` is publicly routed; JSON APIs stay ClusterIP-only.

The child template renders each `valuesFile` entry separately using its `$values/` repository reference and explicitly sets the Helm release name. The fraud-service internal Service is `fraud-service` in the target cluster's `payment-gateway` namespace. Fraud uses the same deployment, service, telemetry, health and security templates as the other Go services.

Flink operator 1.16.1 accepts Kubernetes-style `resources.requests/limits`: each manager requests one CPU; the JobManager requests and limits memory to 1536 MiB, and the TaskManager to 2 GiB. The chart leaves CPU limits unset; operator 1.16.1 derives a one-core CPU limit for each Flink pod with these settings. Parallelism and TaskManager slots are both one. Worker registration allows 10 minutes and slot allocation 15 minutes so a cold image pull can finish before Flink replaces the worker. These waits tolerate startup delay; they do not make recovery faster. The streaming image uses the base distribution’s `FLINK_HOME` JARs and omits the duplicate `apache-flink-libraries` Python package. Checkpoints and savepoints stay in MinIO so recovery can move to another node; local-path volumes cannot supply that shared recovery boundary. Kubernetes HA uses a 60-second lease and 45-second renewal deadline to tolerate observed API stalls; this increases leader-loss detection time compared with the 15-second defaults. The feature chart derives checkpoint, savepoint and HA paths from `streaming.storageRoot` and `epoch`; the feature chart also configures the MinIO endpoint and injects `fraud-flink-storage` credentials from the application Doppler project. The platform owns the operator and bucket policy. Cilium L7 proxying is disabled, so Flink uses L3/L4 DNS access and HTTPS egress to `streaming.storageCIDR` (`10.69.1.101/32`); update that allowlist if the MinIO endpoint address changes. The source-progress observer requests partition end offsets together with one five-second request deadline, avoiding sequential per-partition waits. Parallelism remains one for the resource-constrained cluster. The 2 GiB worker budget requires CI and live state-growth acceptance; the four-payment smoke peak of about 1.06 GiB does not establish sustained capacity.

Gateway service entries inherit `defaults`; each service declares an `image.repository`, with production `digest` and source `revision` pins and an optional development `tag`. A service's `database` selects its database, URL secrets and migration init container; `database.databases` defines owner and additional roles, including Payments' separate runtime role. Service ports also supply probe, route and policy ports, and mesh callers supply network ingress selectors. The chart uses one `externalSecrets` store reference and refresh interval.

The Go application pods are stateless: they use no PVCs or host-path storage. Doppler credentials and integration JSON reach every service through ExternalSecrets and Kubernetes `secretKeyRef` environment variables. No application Secret mounts or file-path settings are used. Restart the affected Deployment after secret rotation; environment variables are read at startup. Postgres owns durable application data and its persistent volume; The idempotency Redis disables disk persistence; authorization and Feast Redis use retained PVCs and AOF with one-second fsync. Redis recovery can lose recent writes; authorization observations report recovery warmup instead of claiming complete counts.

The workspace chart owns the `fraud-ml-prod` Kubeflow Profile (with the same email identity as platform Dex), the namespace-scoped Hub Registry and its database ExternalSecret, RustFS artifact credentials via ExternalSecret, a KFP launcher, and an Argo artifact repository. The generic `secret-store` chart is disabled by default and enabled only through its prod values file. Its token has read-only access to the `payment-gateway-fraud-detection` Doppler project's `prd` config, which holds `KUBEFLOW_REGISTRY_DB_PASSWORD`, `KUBEFLOW_RUSTFS_ACCESS_KEY`, and `KUBEFLOW_RUSTFS_SECRET_KEY`. No secret values are committed to Git. Reconcile the platform first: its Profile controller creates the namespace with ambient mesh enabled. The prod store and workspace Applications retry while the platform CRDs and Profile namespace become available. Kubernetes-native Pipelines are experimental, and the Hub Registry database uses local storage without HA; do not use this workspace with valuable production data until end-to-end validation, backup, and restore are in place.

Provision Kubernetes Secret `fraud-doppler-token` with key `dopplerToken` in the `operators` namespace, using `ESO_DOPPLER_TOKEN` from the consumer Doppler `prd` config. Do not commit or print the token. The ClusterSecretStore and the gateway and workspace ExternalSecrets can then reconcile; re-provision only on token rotation. Delete any `fraud-doppler-token` left in `fraud-ml-prod`. The RustFS access key currently matches the shared platform's bucket-scoped identity, so separate Doppler ownership does not yet imply separate S3 access; provision a distinct RustFS identity before requiring storage isolation. Verify Profile ownership, ExternalSecret readiness, authenticated Dashboard access, and a real pipeline artifact upload and download before calling the workspace operational.

The base `data-pipelines` chart remains disabled by default; the prod child and `values-prod.yaml` explicitly enable the accepted DP1 deployment and daily UTC schedule. The data-pipelines chart owns `fraud-data-prod` workload configuration, lakehouse runtime credentials, Argo pipeline templates and Spark pods. The separate metadata-integrations application owns shared catalog connections, discovery schedules and catalog credentials; the platform owns Argo and persistent OpenMetadata dependencies. Configure scoped runtime credentials, the OpenMetadata bot token, RustFS and OpenMetadata endpoints, resource budgets and immutable Spark and OpenMetadata ingestion image digests; the [historical DP1 instructions](../data-ml/data-pipeline.md#historical-dp1) contain render, execution, replay and rollback commands. Rollback stops workflows and disables the child while retaining warehouse snapshots, reports and platform catalog storage. Existing service/dev rollout defaults are unchanged.

Karapace provides an internal Protobuf-compatible schema registry at `http://schema-registry.payment-gateway.svc.cluster.local:8081`. One registry replica is capped at 256 MiB and stores schemas in Kafka’s compacted `_schemas` topic. The REST proxy is disabled; existing application payloads and Kafka Connect converters are unchanged. The Kafka chart enables `schemaRegistry.registration` in prod: a Job identified by its image and configuration registers the payment, faulty-delivery and label `<topic>-value` schemas from root contracts, with imported schemas registered first and references pinned to their returned versions. Topic `valueSchema` entries supply the contract paths and `<topic>-value` subject names; the Job uses its own repository/digest image pin, registry port and compatibility policy (default `BACKWARD_TRANSITIVE`); incompatible registration or mismatched readback fails the Job. Bounded HTTP and Pod retries tolerate registry startup in the same Kafka Application. If the deadline or retry budget is exhausted, the Job remains failed; after resolving the cause, delete that failed Job for Argo to recreate it, or change its image/configuration. Completed Jobs remain until their identity changes and Argo prunes them; they do not continuously detect registry drift. The `schema-register` image follows the shared commit-tagged publishing and production pin workflow; enabling the Job requires its own published image digest, so initial rollout cannot fall back to an unpublished image. Registration uses the registry HTTP API without Kubernetes API permissions and does not migrate producer/consumer encoding or establish live acceptance.

## Revisions and branch rollouts

Each root uses an anchored `targetRevision` (normally `main`) and reuses `*revision` in `spec.source.helm.valuesObject.global.targetRevision`. For a branch rollout, change the anchored value in the root for that environment to the branch or commit SHA. YAML resolves the same revision for the root catalog and child chart/value sources. Commit the chart changes on that branch, then submit the updated root to that environment's Argo CD using the normal GitOps process. Changing only the live root's `targetRevision` through the Argo UI does not update the embedded child revision: update both fields together or use the anchored source file. The tracked gateway root targets `main`; a temporary branch rollout must be restored to `main` before merge.

CI selects affected images using each entry’s Dockerfile and `inputs` in `.github/service-images.json`; changes to the shared build workflow rebuild all images. Same-repository PRs publish disposable `pr-<number>-<full-sha>` tags; forks build without publication. Main builds publish durable `main-<full-sha>` and `latest` tags and emit repository/digest/revision manifests. After all selected main builds succeed, a generic updater finds matching `image.repository` and `image.digest` mappings in tracked production values, changes only differing digests and their source revisions, and commits with `[skip ci]`. The same repository reference is updated in every consuming chart. The feature chart declares separate Feast and streaming image mappings; the first successful main publication fills their initially empty production digests. Chart templates render immutable `repository@digest` references in production; development values may use a tag. Unaffected images keep their existing pins, and documentation-only changes build no images. PR closure cleans only disposable PR image versions through the shared image manifest. There is no manual release dispatch. Apply the tracked root manifest when its inline application list changes; syncing the existing root alone does not update that list.

## Internal access and rollout prerequisites

Choose the intended workload cluster context and inspect the service with:

```bash
kubectl --context <workload-context> -n payment-gateway port-forward svc/fraud-service 8000:8000
```

The gateway chart creates a `ClusterIP` for fraud exposing gRPC 8000. Kubernetes 1.27+ probes the standard gRPC health service using the `liveness` and `readiness` names. Fraud has no Gateway, HTTPRoute or public ingress. Production rollout acceptance remains outstanding; a later serving increment replaces this layout with a cluster-local Knative Service and a KServe predictor (Knative and KServe serving). Public HTTP traffic belongs at Edge. Gateway Go/fraud pods enroll individually in the existing Istio ambient mesh with strict mTLS and service-account caller policies; the vault serves Edge methods on port 8000 and fixture resolution on port 8001, and its `AuthorizationPolicy` admits only Edge to 8000 and only the processor to 8001. Services speak plaintext gRPC (h2c) inside the mesh; there is no application TLS. Use matching published `main-<full-sha>` image tags for a real rollout, replacing the development `latest` defaults.

The [shared observability guide](shared-observability.md) describes OTLP configuration, metric names, stdout correlation and outstanding deployed acceptance. No application dashboard or alert is installed; telemetry integration is not a rollout prerequisite. Image publication is defined by the [release workflow](../../.github/workflows/release.yml).

## Gateway secrets and local checks

Gateway and workspace ExternalSecrets use the `fraud-doppler` ClusterSecretStore, reading Doppler `payment-gateway-fraud-detection/prd`. Its `secretStore.namespaces` allow-list in `infra/charts/secret-store/values-prod.yaml` covers `fraud-ml-prod`, `fraud-data-prod` and `payment-gateway`, and its bootstrap Secret `fraud-doppler-token` (key `dopplerToken`, from `ESO_DOPPLER_TOKEN`) lives in `operators`, so it survives Profile namespace recreation. The `secret-store` child must sync before the gateway child. Do not hand-create application secrets. Required Doppler keys are:

- `GATEWAY_DB_PAYMENTS_PASSWORD`, `GATEWAY_DB_PAYMENTS_APP_PASSWORD`, `GATEWAY_DB_PAYMENTS_CDC_PASSWORD`, `GATEWAY_DB_NOTIFIER_PASSWORD`, `GATEWAY_DB_VAULT_PASSWORD`, `GATEWAY_DB_PROCESSOR_PASSWORD`.
- `GATEWAY_REDIS_PASSWORD`, `GATEWAY_PAYMENTS_ENCRYPTION_KEY`, `GATEWAY_CHECKOUT_TOKEN_KEY`, `GATEWAY_VAULT_ENCRYPTION_KEY`, `GATEWAY_FINGERPRINT_KEY`, `GATEWAY_CHECKOUT_COOKIE_KEY`.
- `GATEWAY_INTEGRATIONS_JSON`.
- `FLINK_S3_ACCESS_KEY_ID`, `FLINK_S3_SECRET_ACCESS_KEY`: dedicated `fraud-flink-prod` bucket credentials, delivered through the feature chart’s `fraud-flink-storage` ExternalSecret. Restart the Flink job after rotation.

`GATEWAY_INTEGRATIONS_JSON` is an array containing `integration_id` (UUID), `name`, `api_key_sha256` (hex SHA-256), `synthetic`, and optional `webhook: {url, secret, events}`. The synthetic ID must match the historical dataset; `EDGE_SYNTHETIC_FINGERPRINT_KEY=synthetic-fingerprint-v1` is non-secret. Real integrations use the secret fingerprint key. The marketplace receiver is `http://web.ecommerce.svc.cluster.local:8080/webhooks/payment-gateway`, with subscriptions `attempt.declined`, `payment.succeeded`, `payment.expired`. Keep notifier egress destinations in its chart values aligned with configured webhook URLs; HTTPS endpoints require corresponding explicit destination rules.

Enter `devenv shell`, which generates bindings and sqlc queries. For a relevant module, use `cd src/payment-gateway/<module>; GOWORK=off go test -short ./...; GOWORK=off golangci-lint run ./...`. Full `go test -race -count=1 ./...` starts shared testcontainers-go dependencies for PostgreSQL, Valkey and Kafka as needed, both locally and in CI. Docker is required unless `-short` is set; there are no `TEST_*` overrides, silent integration skips or CI service containers. The single `src/payment-gateway/shared` Go module groups protobuf bindings, test utilities and common runtime/security packages; services use `replace ../shared` and build with `GOWORK=off`. The optional local workspace is `src/payment-gateway/go.work`; run workspace commands from that directory or a service directory. `bash scripts/ci-checks.sh go` discovers and checks every service and the shared module; CI owns the full check/image sweep. End-to-end smoke and access checks run only on the prod Kubernetes cluster after GitOps rollout, without manually running services or databases in Docker.
