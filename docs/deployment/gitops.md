# GitOps deployment

GitOps deploys the same gateway and data charts to dev and prod. The platform owns Talos, Argo CD, Kubeflow and its `ml` workspace, Polaris and StarRocks servers, OpenMetadata, operators, External Secrets and ingress. This repository owns gateway services in `payment-gateway` and its pipeline, Flink and Feast workloads in `data`.

The roots are `infra/argocd/dev/root.yaml` and `infra/argocd/prod/root.yaml`, tracking `deploy/dev` and `deploy/prod`. Each published release records one chart source revision and per-service commit-based image tags in `infra/argocd/app-of-apps/release.yaml`. CI writes only the deployment branch; it does not change main, contact Kubernetes or hold cluster credentials.

| Environment | Release branch | Gateway hostname | Storage |
| --- | --- | --- | --- |
| Dev | `deploy/dev` | `pay-gateway-dev.phuchoang.sbs` | MinIO `platform-dev`, local-path PVCs |
| Prod | `deploy/prod` | `pay-gateway.phuchoang.sbs` | AWS platform bucket, gp3 PVCs |

Gateway and Kafka children target `payment-gateway`; feature workloads target `data` in both environments. The `infra/charts/payment-gateway` application chart owns all six Go services, including fraud, through one `services` map plus the gateway database, idempotency and authorization Redis resources, secrets, routing and policies. The independent `infra/charts/fraud-features` chart owns Flink, the Feast writer/server and Feast Redis; the platform owns the Flink operator in `operators`. The chart declares five CNPG databases with separate roles; Payments and Fraud use owner roles for migrations and restricted `payments_app` / `fraud_app` runtime roles. Payments has a separate replication principal restricted to the event ledger. Three operator-managed Redis resources isolate idempotency, authorization observations and Feast, each with independent credentials, clients, memory limits and noeviction. Gateway `features.enabled` is enabled in both environments for shadow Fraud retrieval through `features.url`; rules remain authoritative and authorization counters remain observe-only. Existing CI integration tests and bounded live evidence define this shadow/observe-only slice; full replay, sustained load and broad outage acceptance remain unverified. The feature chart independently controls `feast.enabled` and `streaming.enabled`, both true by default; enabling Feast adds its SDK writer, official server and Redis. Both charts must use the same epoch and definition hash. The writer runs one replica with Recreate upgrades; no offline writer may target its active keys. Its registry is reconstructed from code in ephemeral memory. The feature journal is `fraud.feature-updates.v1.live-v17`; replay uses a separate topic and epoch. Kafka/Connect publish ledger bytes to the internal `payments.events.v1` topic. Only Edge `/checkout/*` is publicly routed; JSON APIs stay ClusterIP-only.

Each child reads its environment values from the immutable chart source and receives the per-service image tags as Helm values. No chart or value repository overrides are supported. The fraud-service Service remains `fraud-service.payment-gateway.svc.cluster.local:8000`.

Flink operator 1.16.1 accepts Kubernetes-style `resources.requests/limits`: each manager requests one CPU; the JobManager requests and limits memory to 1536 MiB, and the TaskManager to 2 GiB. The chart leaves CPU limits unset; operator 1.16.1 derives a one-core CPU limit for each Flink pod with these settings. Parallelism and TaskManager slots are both one. Worker registration allows 10 minutes and slot allocation 15 minutes so a cold image pull can finish before Flink replaces the worker. These waits tolerate startup delay; they do not make recovery faster. The streaming image uses the base distribution’s `FLINK_HOME` JARs and omits the duplicate `apache-flink-libraries` Python package. Checkpoints and savepoints stay in environment object storage so recovery can move to another node; local-path volumes cannot supply that shared recovery boundary. Kubernetes HA uses a 60-second lease and 45-second renewal deadline to tolerate observed API stalls; this increases leader-loss detection time compared with the 15-second defaults. The feature chart derives checkpoint, savepoint and HA paths from `streaming.storageRoot` and `epoch`; the feature chart also configures the environment endpoint and injects `gateway-flink-storage` credentials from gateway Doppler. The platform owns the operator, bucket and gateway storage policy. Flink uses DNS, Kubernetes API access, cross-namespace Kafka access and HTTPS egress without a fixed MinIO IP allowlist. The source-progress observer requests partition end offsets together with one five-second request deadline, avoiding sequential per-partition waits. Parallelism remains one for the resource-constrained cluster. The 2 GiB worker budget passed CI and bounded live verification with a worker peak of about 867 MiB; sustained state-growth/load acceptance remains pending. CPU savings have not been measured, and startup remains slow under observed CPU throttling and host I/O pressure.

Gateway services inherit `defaults` and declare their image repository. Release values supply a `global.imageTags` map keyed by image repository to every chart. Unchanged services keep their prior tags; service revision fields follow their own image commit. Chart defaults use `dev` for local rendering; bootstrap only the published environment release root. Database selection, service ports, mesh callers and ExternalSecrets remain service-owned.

The Go application pods are stateless: they use no PVCs or host-path storage. Doppler credentials and integration JSON reach every service through ExternalSecrets and Kubernetes `secretKeyRef` environment variables. No application Secret mounts or file-path settings are used. Restart the affected Deployment after secret rotation; environment variables are read at startup. Postgres owns durable application data and its persistent volume; The idempotency Redis disables disk persistence; authorization and Feast Redis use retained PVCs and AOF with one-second fsync. Redis recovery can lose recent writes; authorization observations report recovery warmup instead of claiming complete counts.

Kubeflow configuration, artifact credentials and launcher configuration come from the platform in `ml`; the gateway does not create a Profile, launcher, registry or artifact repository. Gateway runtime secrets use `gateway-doppler`, selecting application Doppler `dev` or `prd`. Create `payment-gateway/doppler-token` with key `dopplerToken` from a read-only token for the selected config before applying the AppProject and environment root. The shared `data` and `ml` namespaces must already exist.

Apply the platform repository’s `terraform/cluster/env/dev/minio-gateway-policy.json` to a dev MinIO identity for the existing `platform-dev` bucket. Store its credentials in gateway Doppler `payment-gateway-fraud-detection/dev` as `OBJECT_GATEWAY_ACCESS_KEY_ID` and `OBJECT_GATEWAY_SECRET_ACCESS_KEY`. Platform foundation Terraform provisions the matching AWS identity using its own gateway storage policy and writes prod keys to gateway Doppler `prd`. Flink, lakehouse runtime, metadata storage connections and synthetic writing share this one identity per environment; remove the old gateway storage keys instead of maintaining aliases. Application charts use `gateway-doppler` for storage and application credentials. The platform `doppler` store supplies the existing Polaris client secret and StarRocks admin and reader passwords to the integration setup; metadata ingestion also reads the platform reader password.

Both environment values enable DP1 workflow templates; recurring schedules remain disabled until the new source is published and validated. The data-pipelines chart owns workflow configuration, external secret references and Spark execution resources in platform-owned `data`. The separate metadata-integrations application owns catalog connections and discovery schedules. Configure the OpenMetadata bot token in the gateway Doppler config and use the platform Polaris and StarRocks endpoints. The [historical DP1 instructions](../data-ml/data-pipeline.md#historical-dp1) describe execution and metadata replay. Disabling these applications retains shared services and durable objects.

Karapace provides an internal Protobuf-compatible schema registry at `http://schema-registry.payment-gateway.svc.cluster.local:8081`. One registry replica is capped at 256 MiB and stores schemas in Kafka’s compacted `_schemas` topic. The REST proxy is disabled; existing application payloads and Kafka Connect converters are unchanged. Both environment values enable `schemaRegistry.registration`: a Job identified by its image and configuration registers the payment, faulty-delivery and label `<topic>-value` schemas from root contracts, with imported schemas registered first and references pinned to their returned versions. Topic `valueSchema` entries supply the contract paths and `<topic>-value` subject names; the Job uses its own image repository with its service commit tag, registry port and compatibility policy (default `BACKWARD_TRANSITIVE`); incompatible registration or mismatched readback fails the Job. Bounded HTTP and Pod retries tolerate registry startup in the same Kafka Application. If the deadline or retry budget is exhausted, the Job remains failed; after resolving the cause, delete that failed Job for Argo to recreate it, or change its image/configuration. Completed Jobs remain until their identity changes and Argo prunes them; they do not continuously detect registry drift. The `schema-register` image follows the shared environment release workflow; CI publishes its image before updating the deployment branch. Registration uses the registry HTTP API without Kubernetes API permissions and does not migrate producer/consumer encoding or establish live acceptance.

## Revisions and branch rollouts

Trusted PRs build and publish affected application images, then publish a complete release on `deploy/dev`. Main builds publish a complete release on `deploy/prod`. CI compares each image’s dependencies against its last deployed commit; shared code rebuilds its consumers, while chart-only releases reuse all tags. The first release builds every image. Fork PRs build without publication. Images carry `pr-<number>-<full-sha>` or `main-<full-sha>` tags; deployment retains prior tags for unchanged images in `global.imageTags`, keyed by repository, without digest manifests. Publication waits for all affected image builds and skips a source revision that has already been superseded. Commit tags must not be repurposed for different source code. No image pin commits, mutable `latest` tags or PR-close image deletion are used.

Apply the AppProject and the selected environment root once after the release branch exists. Argo CD then reads the release branch, which selects child chart sources at the release commit and their per-service image tags. Bootstrap the `payment-gateway` namespace and its Doppler token before the roots; shared namespaces and controllers come from the platform.

## Runtime configuration

Python services do not accept CLI configuration overrides. Historical generation reads `configs/historical-smoke.yaml` by default; `SIMULATOR_CONFIG` can select a different YAML. Live traffic uses its dedicated `simulator.live.runtime` module and defaults to `/etc/simulator/live.yaml`, also overridable with `SIMULATOR_CONFIG`. Generation controls (`prepare_only`, `takeover_stopped_writer`, `allow_small_dataset`) belong under YAML `execution`.

Bronze and its metadata stages use `PIPELINE_STAGE`; metadata integrations use `METADATA_STAGE` and optional `METADATA_CONNECTOR`. Profiling uses `PROFILE_REFRESH=true|false`. `SOURCE_ROOT`, `EVIDENCE_ROOT`, `DATASET_VERSION`, storage endpoint settings and secret references remain environment configuration supplied by Helm. Feast serving and writing use dedicated modules, and the archiver uses `simulator.landing.runtime`; no mode flags are needed.

All services validate configuration at startup and exit non-zero with a sanitized diagnostic on invalid values. Boolean switches accept only `true` or `false` (case-insensitive).

## Internal access and rollout prerequisites

Choose the intended workload cluster context and inspect the service with:

```bash
kubectl --context <workload-context> -n payment-gateway port-forward svc/fraud-service 8000:8000
```

The gateway chart creates a `ClusterIP` for fraud exposing gRPC 8000. Kubernetes 1.27+ probes the standard gRPC health service using the `liveness` and `readiness` names. Fraud has no Gateway, HTTPRoute or public ingress. Production rollout acceptance remains outstanding; a later serving increment replaces this layout with a cluster-local Knative Service and a KServe predictor (Knative and KServe serving). Public HTTP traffic belongs at Edge. Gateway Go/fraud pods enroll individually in the existing Istio ambient mesh with strict mTLS and service-account caller policies; the vault serves Edge methods on port 8000 and fixture resolution on port 8001, and its `AuthorizationPolicy` admits only Edge to 8000 and only the processor to 8001. Services speak plaintext gRPC (h2c) inside the mesh; there is no application TLS. Use the published environment release, which supplies each application image’s commit-based tag.

The [shared observability guide](shared-observability.md) describes OTLP configuration, metric names, stdout correlation and outstanding deployed acceptance. No application dashboard or alert is installed; telemetry integration is not a rollout prerequisite. Image publication is defined by the [release workflow](../../.github/workflows/release.yml).

## Gateway secrets and local checks

Application ExternalSecrets use `gateway-doppler`, selecting `payment-gateway-fraud-detection/dev` in dev or `prd` in prod. Its bootstrap Secret is `payment-gateway/doppler-token`, key `dopplerToken`. Create a read-only token for the corresponding config; the secret-store child must become ready before application secrets can reconcile. Required application keys are:

- `GATEWAY_DB_PAYMENTS_PASSWORD`, `GATEWAY_DB_PAYMENTS_APP_PASSWORD`, `GATEWAY_DB_PAYMENTS_CDC_PASSWORD`, `GATEWAY_DB_FRAUD_PASSWORD`, `GATEWAY_DB_FRAUD_APP_PASSWORD`, `GATEWAY_DB_NOTIFIER_PASSWORD`, `GATEWAY_DB_VAULT_PASSWORD`, `GATEWAY_DB_PROCESSOR_PASSWORD`.
- `GATEWAY_REDIS_PASSWORD`, `GATEWAY_AUTHORIZATION_REDIS_PASSWORD`, `GATEWAY_FEAST_REDIS_PASSWORD`, `GATEWAY_PAYMENTS_ENCRYPTION_KEY`, `GATEWAY_CHECKOUT_TOKEN_KEY`, `GATEWAY_VAULT_ENCRYPTION_KEY`, `GATEWAY_FINGERPRINT_KEY`, `GATEWAY_CHECKOUT_COOKIE_KEY`.
- `GATEWAY_INTEGRATIONS_JSON`, `OPENMETADATA_TOKEN`; `GATEWAY_SYNTHETIC_API_KEY` when simulation is enabled.

The gateway `gateway-doppler` store supplies `OBJECT_GATEWAY_ACCESS_KEY_ID`, `OBJECT_GATEWAY_SECRET_ACCESS_KEY` and `STARROCKS_OPENMETADATA_PASSWORD`. The platform `doppler` store supplies only shared administrative authentication (`ICEBERG_CLIENT_SECRET` and `STARROCKS_ROOT_PASSWORD`) to the integration chart. Restart consuming workloads and rerun the integration setup after credential rotation.

`GATEWAY_INTEGRATIONS_JSON` is an array containing `integration_id` (UUID), `name`, `api_key_sha256` (hex SHA-256), `synthetic`, and optional `webhook: {url, secret, events}`. The synthetic ID must match the historical dataset; `EDGE_SYNTHETIC_FINGERPRINT_KEY=synthetic-fingerprint-v1` is non-secret. Real integrations use the secret fingerprint key. The marketplace receiver is `http://web.ecommerce.svc.cluster.local:8080/webhooks/payment-gateway`, with subscriptions `attempt.declined`, `payment.succeeded`, `payment.expired`. Keep notifier egress destinations in its chart values aligned with configured webhook URLs; HTTPS endpoints require corresponding explicit destination rules.

Enter `devenv shell` for generated bindings, formatting and lint tools. Run local non-test checks with `bash scripts/ci-checks.sh helm` and relevant linters. CI runs the full Python and Go checks, integration tests and image builds; do not run tests locally.

## Object storage and fresh rollout

Both environments use the same prefixes: `datasets/payment-gateway/` for historical and streaming source, `runs/payment-gateway/` for DP1 evidence and Flink state, and the platform `lakehouse/` prefix through Polaris for Iceberg tables. Kubeflow owns `artifacts/`. Never tag active Flink state with `expire=true`, which enables the platform finished-run lifecycle rule. Bucket names have no special meaning to application code. Set `S3_ENDPOINT`, `S3_PATH_STYLE`, and `AWS_REGION` for runtime storage access; set YAML `output: s3://<bucket>/datasets/payment-gateway` to select the destination.

Existing gateway datasets, Kafka offsets, feature epochs and checkpoints are not migrated. Generate a fresh v17 source before enabling the live simulator, set its actual manifest digest, and start fresh streaming state. Data-pipeline schedules remain disabled until the new source and catalog credentials are verified. No dataset has been rebuilt merely by changing the charts. Apply only gateway-owned cleanup; never empty the shared platform bucket or delete shared namespaces.

The `lakehouse-integration` chart owns Polaris registration, the StarRocks external catalog and SQL reader, and the `iceberg-storage` Secret consumed by the platform Polaris Deployment. Shared servers and their database/PVC resources remain platform-owned. The platform no longer creates a separate `OBJECT_LAKEHOUSE_*` identity. Reconcile this chart before expecting Polaris readiness; its storage Secret is a required platform input.

For prod access, review and apply the platform foundation plan. The gateway repository needs no Terraform stack or AWS provisioning credentials. Provision the gateway identity before retiring the platform's old lakehouse identity. Coordinate the platform/chart ownership handoff for `iceberg-storage`; do not delete the bucket, catalog database, tables or shared namespaces. Dev MinIO access remains externally provisioned using the platform's policy file.
