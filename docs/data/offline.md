# Offline data

The offline path turns a reproducible synthetic history into curated tables. The historical generator writes immutable per-day Parquet datasets to object storage, standing in for an export from another department; DP1 ingests them into Bronze, DP2 curates Silver, and DP3 (planned) computes offline features. Each data problem the generator introduces is solved by a pipeline stage.

- Generator code: [`src/data-pipeline/simulator/simulator`](../../src/data-pipeline/simulator/simulator) (`world.py`, `lifecycle.py`, `historical.py`, `store.py`).
- Pipeline status: **in progress** in [PR #102](https://github.com/phuchoang2603/payment-gateway-fraud-detection/pull/102), designed by the [`rebuild-generation-to-silver`](../../openspec/changes/rebuild-generation-to-silver/design.md) change. Each pipeline is an Argo workflow that writes, audits and publishes: the Spark stage writes to an audit branch of each Iceberg table, the checks stage runs the ClickHouse SQL checks against that branch, and only when every check passes does `publish-tables` fast-forward the tables' main branch. An exit handler publishes the run to OpenMetadata; see [orchestration and governance](orchestration-governance.md).

## Data problems and how they are solved

| Problem | Generated by | Solved by | Evidence |
|---|---|---|---|
| Skew | Half of ordinary purchases go to one hot merchant (`world.behavior.hot_merchant_share`); the rest follow Zipf merchant and category popularity and each customer's familiar merchants | Benchmark of counts and amounts per merchant and day as a sort-merge join with three variants: AQE skew join off, AQE skew join on, and salting into 16 buckets. Each variant runs once and is checked against the baseline by row count and checksum | Generated: top merchant 56.3% (v18), about 56% (v19 sample). Solved: pending, one timed run per variant on v19 Silver with equal checksums and Spark UI stages |
| Schema evolution | Events before the change date are `schema_version` 2 in `.v2` files that physically lack the fields the contract declares `sinceSchemaVersion: 3`; later events go to `.v3` files (`schema_changes`) | DP1 reads both with `mergeSchema` (absent fields become null) and casts once to the Bronze contract | Generated: every `.v2` file lacks `assessment_id`, every `.v3` file has it. Solved: pending, one Bronze query on v18 showing the v3-only fields null on `schema_version` 2 rows and filled on `schema_version` 3 rows |
| Duplicates | A share of events is republished with the same `event_id` and content but a `recorded_at` 1–300 seconds later (`duplicate_rate`) | DP2 deduplicates on `event_id` ignoring `recorded_at` and keeps the earliest; any other difference sends the whole payment to `silver.rejected_events` | Generated: 1.996% (v18). Solved: pending, from the Silver run report's duplicate and conflict counts |
| High cardinality | Millions of customers, payment methods, devices and addresses (`world.counts`) | Not benchmarked in this change; customer, payment method and device are kept as Bronze and Silver columns | Not applicable |
| Delayed labels | Simulation truth at the end of an attempt; chargebacks for successful fraud 7–21 days later, reported with a configured probability (`world.label_delays`) | DP2 classifies each label `linked`, `pending` or `violation` against the attempt's start and success; consumers join only labels available before their cutoff | Pending |

The published interface is the contracts: [payment events](products/historical-payments/payment-events.md) and [fraud labels](products/historical-payments/fraud-labels.md).

### Configuration

Configurations are YAML files baked into the simulator image under `/app/configs`:

| File | Dataset | Purpose |
|---|---|---|
| `historical-dev.yaml` | `v18`, 90 days from 2026-07-31 to 2026-10-28, 10k customers, schema change on 2026-09-15 | Development source in `platform-dev` |
| `historical-full.yaml` | `v19`, 365 days from 2025-10-29 to 2026-10-28, about 3M customers, schema change on 2026-04-30 | Full-scale source in the prod bucket; `minimum_source_bytes` is 100 GB |

Top-level keys hold only the logical dataset:

- `dataset_version`, `duration_days`, `duplicate_rate` (the share of events republished with a later `recorded_at`)
- `world.behavior.hot_merchant_share`: the share of ordinary purchases that go to the first merchant key; the Zipf tail takes the rest
- `minimum_source_bytes`: publication refuses a dataset whose physical Parquet bytes are below this value
- `schema_changes`: ordered `{effective_at, version}` entries. Event schema versions start at 2; a change to version 3 makes the fields declared with `sinceSchemaVersion: 3` in the payment-events contract present from `effective_at` (version 3 is the gateway's current shape)
- `output`: a local directory or an `s3://bucket/prefix` root without credentials
- `world`: `seed`, `integration_id`, `synthetic_key`, `start_date`, entity `counts`, purchase `behavior`, `scenarios`, `label_delays`

Credentials are never read from the configuration.

### Dates and label availability

Purchase-start days end on the last full day before the run, so the history reaches the present and recent windows are full. Lifecycle tails and delayed chargeback labels keep their real timestamps, so some labels have a `label_available_at` after the generation date and are not yet available. Consumers apply an as-of cutoff to `label_available_at` and `occurred_at` for any training or feature use.

### Settings

Run settings come from the environment:

- `GENERATOR_MODE`: `generate` (all days in one process), `shard` (one shard of the days) or `publish` (the manifest, once every day has a marker)
- `SHARD_INDEX`, `SHARD_COUNT`: the shard, used in `shard` mode
- `GENERATOR_WORKERS`: parallel processes in one pod; the chart sets it from `generator.workers`
- `GENERATOR_CONTRACTS`: the historical-payments contract directory (defaults to `/app/contracts/historical-payments` in the image)
- `SIMULATOR_CONFIG`: the YAML configuration

The workflow sets these per step. Locally:

```bash
cd src/data-pipeline/simulator
SIMULATOR_CONFIG=/path/to/copied.yaml GENERATOR_CONTRACTS=../../../contracts/data-products/historical-payments uv run --locked simulator
```

### Running

In the cluster, the environment selects its configuration, shard count, workers and resources through the data-pipelines chart (`generator.config`, `generator.shards`, `generator.workers`, `generator.resources`). Prod runs one shard per spot node in the `aws-cpu-burst` pool. Each shard pod generates the purchase-start days whose index modulo the shard count matches its shard, and a final publish pod writes the manifest. Submit a run with:

```bash
argo submit -n data --from workflowtemplate/generate-historical
```

### Output

Each dataset is written below `historical/<dataset_version>/`:

- `config.json`: the logical configuration, the generator digest and their hash, written first
- `payment_events/date=YYYY-MM-DD/part-NNNNN.v2.parquet` and `.v3.parquet`: payment events by `schema_version`, so each file's Parquet schema has exactly the fields its version declares
- `fraud_labels/date=YYYY-MM-DD/part-NNNNN.parquet`: labels
- `date=YYYY-MM-DD/_day.json`: written after all parts of a purchase-start day, listing their rows, bytes and SHA-256
- `manifest.json`: written last and only if absent, with the configuration, generator digest, contract identities, row and byte totals and the file list

The generator digest is a SHA-256 over the generator source files, the calibration file and the historical contracts. A rerun with the same configuration and digest skips complete days and regenerates incomplete ones, producing the same bytes. A rerun with a different configuration or digest is refused, and so is any version that already has a manifest.

## Pipeline

### DP1: raw → Bronze

Bronze keeps every delivery, including duplicates, in two tables shared by both sources: `bronze.payment_events` and `bronze.fraud_labels`.

- **Historical mode** lists the dataset root once (metadata only) and fails before reading if its parquet objects differ from the manifest's paths or sizes. It then reads the `.v2` and `.v3` files once, together, with `mergeSchema` (absent version-2 fields become null), casts losslessly to the Bronze contract and replaces only that dataset version's rows. After writing it groups the rows by source file and fails, naming the file, when a count differs from the manifest. The generator's SHA-256 values are not recomputed.
- **Kafka mode** reads `payments.events.v1` and `fraud.labels.v1` directly, decodes protobuf with the payments descriptor set, and appends. Each run starts from `max(_kafka_offset) + 1` per partition, read from Bronze itself, so progress and rows commit together and survive compaction. Records that fail protobuf decoding or a required-field check go to `bronze.rejected_records` instead of blocking later runs. The error names the first failing check, and an empty string counts as missing. A record that decodes but cannot be cast to the Bronze schema fails the run.
- **Provenance columns:** `_source`, `_dataset_version`, `_source_file`, `_kafka_topic`, `_kafka_partition`, `_kafka_offset`, `_kafka_timestamp`, `_ingested_at`, `_run_id`.

### DP2: Bronze → Silver

DP2 has two modes. `historical`, the default, is a full recompute from Bronze snapshots fixed at the start of the run. `incremental`, used by the Kafka schedule, reads only the Bronze rows appended since the snapshots the last DP2 run recorded (an Iceberg incremental read), recomputes every payment they name from all of its Bronze rows within a 35-day lookback, and replaces those payments' rows. Every Silver rule is local to one payment, so the result equals a historical run over the same Bronze; when it cannot be exact (no previous run, a historical Bronze reload, changed curation logic, or history older than the lookback) the run fails and asks for historical mode. Consumers read what a run changed through Iceberg's changelog view of the Silver tables. Either mode writes these tables:

- **`silver.payment_events`:** one row per `event_id`. Republished copies (same content, later `recorded_at`) collapse to the earliest. Copies that differ in any other business field are conflicts: the whole payment goes to `silver.rejected_events`.
- **`silver.attempts`:** one row per attempt with `customer_id`, `merchant_id`, `payment_method_fingerprint`, `amount_minor`, server start time, client `attempted_at`, risk decision, outcome and payment status. Lifecycle violations fail the checks.
- **`silver.labels`:** one row per distinct label observation, classified `linked`, `pending`, `orphan` or `violation` against the payment, the attempt's start and success. A historical label whose payment has no events is an `orphan`; a live label whose payment has not arrived is `pending`. Violations and orphans fail the checks.

A run report records the Bronze snapshot IDs, input rows, duplicates, conflicts, rejected rows, label linkage counts, the Silver snapshot IDs with their added records, and the tasks, stages and wall time of each phase. The report is written last, after every table write.

### Viewing Spark event logs

Every Spark application writes a rolling event log to `runs/payment-gateway/spark-events/` in the environment's bucket, so its UI can be read after the run ends. To view it, start a throwaway History Server from the `data-platform-spark` image with the release's tag, read from `infra/argocd/app-of-apps/release.yaml`:

```sh
kubectl -n data run spark-history --restart=Never --image=<data-platform-spark image> --overrides='{"spec":{"containers":[{"name":"spark-history","image":"<data-platform-spark image>","command":["/bin/sh","-c"],"args":["SPARK_HISTORY_OPTS=\"-Dspark.history.fs.logDirectory=<event log dir> -Dspark.hadoop.fs.s3a.endpoint=$S3_ENDPOINT -Dspark.hadoop.fs.s3a.path.style.access=$S3_PATH_STYLE -Dspark.hadoop.fs.s3a.access.key=$AWS_ACCESS_KEY_ID -Dspark.hadoop.fs.s3a.secret.key=$AWS_SECRET_ACCESS_KEY\" exec /opt/spark/bin/spark-class org.apache.spark.deploy.history.HistoryServer"],"envFrom":[{"secretRef":{"name":"gateway-storage"}}],"env":[{"name":"S3_ENDPOINT","value":"<S3_ENDPOINT>"},{"name":"S3_PATH_STYLE","value":"<S3_PATH_STYLE>"}],"ports":[{"containerPort":18080}]}]}}'
kubectl -n data port-forward pod/spark-history 18080:18080
```

Use the event log directory and the `S3_ENDPOINT` and `S3_PATH_STYLE` values from the environment's `values-<env>.yaml`. Open `http://localhost:18080`, then delete the pod with `kubectl -n data delete pod spark-history` when finished. The image has `spark-class` but not `start-history-server.sh`, so the command starts the server class directly.

### DP3: offline features

**Planned.** A daily Spark batch over Silver computes point-in-time features per customer and payment method, including the long 7- and 30-day windows that the streaming path does not keep, and materializes them into Feast. See [feature store](../ml/feature-store.md).

### Schemas and naming

Bronze and Silver table schemas are the v1 Bronze and Silver data-product contracts, with generated references under [`products/`](products). Gold dimension and fact tables (SCD2 `valid_from_ts`, `valid_to_ts`, `is_current`) and `feat_` tables with `event_timestamp` and `created` are planned with DP3.
