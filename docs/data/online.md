# Online data

The online path is live gateway traffic. The live simulator drives the gateway's public APIs at current time, Payments writes authoritative events that reach Kafka through outbox CDC, and a PyFlink job turns them into v2 window features on the feature journal topic `fraud.feature-updates.v2.<epoch>`, with per-record rejects on `fraud.feature-rejects.v1.<epoch>`. The journal feeds the `feature-writer` Deployment: each batch is pushed to Redis through Feast, then buffered rows are appended to `gold.feat_stream_*` with their Kafka offsets in the same Iceberg commit. Go Fraud reads `payment_risk_v1` in shadow mode. Bronze also ingests the same topics in Kafka mode; see [offline data](offline.md).

- Simulator code: [`src/data-pipeline/simulator/simulator/live`](../../src/data-pipeline/simulator/simulator/live). Streaming code: [`src/data-pipeline/streaming`](../../src/data-pipeline/streaming); deployment: [`infra/charts/data-pipelines`](../../infra/charts/data-pipelines).
- Status: the live simulator is disabled in dev and enabled for a seven-day v19 run in prod at one payment every 30 seconds; `data-pipelines.features.enabled` runs Flink `live-v19`, the feature writer, Redis and the Feast server in prod, and the `live-v18` equivalents in dev. Dev simulator values point at the v18 historical manifest and its SHA-256. The Flink job implements feature contract v2 under `live-v18` in dev and `live-v19` in prod.

    pay -->|"outbox"| cdc["Debezium CDC"] -.-> ev[("payments.events.v1")]

## Data problems and how they are solved

| Problem | Generated by | Solved by | Evidence |
|---|---|---|---|
| Late arrivals | Store-and-forward clients: a seeded share of attempts is held for a configured delay, then submitted with the original click time as `simulated_client.attempted_at` | Flink counts each attempt in the windows its `attempted_at` falls in, producing a new revision without changing served snapshots. Attempts older than the 24-hour horizon increment the `too_late` metric and are logged, without failing the job | Dev run: 178 of 3,590 attempts (4.96%) arrived 5–15 minutes late against 5% configured; replay benchmark: 0 of 3,234 cells wrong when handled, 274 with arrival-time windows. See [Evidence](#evidence) |
| Duplicates | Redelivery: a seeded share of committed events is re-published to `payments.events.v1` as byte-identical copies on the same partition, on top of at-least-once CDC | Flink deduplicates by `event_id`, then by attempt identity, dropping identical copies and dead-lettering conflicting content; that state expires 25 hours after the attempt time, so a later copy is already too late. Bronze keeps every delivery and Silver deduplicates | Dev run: 265 extra deliveries over 18,133 unique events (1.46%) against 1.5% configured, all dropped by Flink; replay benchmark: 850 over-counted values without dedup, 0 when handled. See [Evidence](#evidence) |
| Poison records | Malformed or undecodable events, invalid attempt context, or conflicting content under one event or attempt identity | Flink writes them to `fraud.feature-rejects.v1.<epoch>` through a side output while the job keeps running. The value is the original bytes, the key is the `event_id` when decodable, and headers carry the error class, a short message and the source topic, partition, offset and timestamp. Rejects commit exactly-once with the checkpoint, and each one increments a per-class `rejected` metric. Invariant violations such as offset regression or state limits still fail the job | Dev run: none injected; the reject topic stayed empty and no `rejected` metric registered. |
| Restarts | Pod or node loss | Checkpoint recovery restores offsets and state; journal and reject writes commit exactly-once with the checkpoint | Dev run: TaskManager deleted at 11:51:38 UTC, job restored from checkpoint 181 2.4 s later, first new checkpoint 65 s after deletion; 13,159 journal updates with no repeated or conflicting revisions. See [Evidence](#evidence) |

## Live simulator

- Tokenizes synthetic cards, creates payments and submits attempts through Edge with run-scoped idempotency keys; retries reuse the same key and content.
- Publishes simulation-truth labels after each attempt and schedules chargebacks for successful fraud on `fraud.labels.v1`. Label availability is the actual publication time. The schedule is held in memory, so an interrupted run reports unfinished labels instead of claiming them.
- Configuration comes from `SIMULATOR_CONFIG`, rendered by the `live-traffic` chart.
- Store-and-forward lateness: `late_rate` (default 0) selects attempts held for `late_min_seconds`–`late_max_seconds` (300–600) and bounded by `max_held_attempts`. Edge accepts `simulated_client.attempted_at` only from synthetic integrations and rejects times after server time. Attempts still held at shutdown are reported as unsent.
- Redelivery: `redelivery.enabled` (default off) and `redelivery.rate` (0.015). Copies carry an `x-simulator-redelivery` header and are never copied again. Offsets commit after the copy is acknowledged, so a restart can add copies.

The simulator continues the historical entity world: it rebuilds the world from the manifest's recorded configuration and checks the manifest's `world_digest` before sending anything.

## Streaming features

### Runtime

- Flink and PyFlink 2.2.1 on the platform's Flink operator, Kubernetes HA, checkpoints and savepoints in object storage under `runs/payment-gateway/flink/`.
- Parallelism one; each manager requests one CPU, the TaskManager 2 GiB.
- Each epoch has its own feature journal topic and state; a state layout change starts a fresh epoch instead of restoring incompatible state.
- Per-record data errors go to `fraud.feature-rejects.v1.<epoch>`. This is the real-time triage path, not the durable copy: Bronze Kafka mode independently keeps every raw delivery, in `bronze.rejected_records` or the Bronze tables.

### Windows

The job reads only `attempt_started` events, keyed on the client `attempted_at`; risk decisions do not gate contributions. Per-customer and per-method attempt counts over 5 minutes, 1 hour and 24 hours, plus distinct customer devices over 24 hours, cover `[t − window, t)`. Per-window coverage stays unknown until the job has run for that window's length, and missing history is null, never zero. An attempt time after its observed availability fails the job. Long 7- and 30-day windows are computed offline by DP3, not by Flink; there is no HybridSource bootstrap. See [feature store](../ml/feature-store.md).

### Window code

Each customer or payment-method `Entity` in [`model.py`](../../src/data-pipeline/streaming/fraud_streaming/model.py) keeps its attempts in keyed Flink state and advances to the current anchor `now`. Expiry first, then admission:

```python
for window in WINDOWS:
    expirations = self.expirations[window]
    while expirations and expirations[0][0] <= now:
        _, identity = heapq.heappop(expirations)
        entry = self.entries[identity]
        self.counts[window] -= 1
        ...
while self.pending and self.pending[0][0] <= now:
    _, identity = heapq.heappop(self.pending)
    entry = self.entries[identity]
    if entry.started_at < now - DAY:
        del self.entries[identity]
        continue
    for window in WINDOWS:
        if entry.started_at < now - window:
            continue
        self.counts[window] += 1
        # The inclusive lower boundary expires one microsecond after start + window.
        heapq.heappush(self.expirations[window], (entry.started_at + window + 1, identity))
```

- **Windows by attempt time.** `WINDOWS` is 5 minutes, 1 hour and 24 hours. An attempt joins a window when its `attempted_at` (`started_at`) is in `[now − window, now)`.
- **Pending first.** A new attempt waits in `pending` until one microsecond after its start, so an attempt never counts in a snapshot anchored at its own start time.
- **Late attempts.** An attempt arriving late joins every window it still falls in, and is skipped entirely if it's already older than 24 hours.
- **Expiry heaps.** Each window has a heap of expiry times, so evicting old attempts costs O(log n) per attempt instead of rescanning history. The job registers one Flink timer at the earliest pending or expiry boundary, so counts drop even when the customer is quiet.
- **Revisions.** After each advance, the job compares the coverage, values, counts and source progress with the previous snapshot. Only a change increments `revision` and moves `write_at` forward, so redelivered or idle inputs produce no new revision, and a late attempt produces a new revision without changing earlier ones.

### Metrics

| Metric | Meaning |
|---|---|
| `too_late` | Attempts older than the 24-hour horizon when processed; dropped and logged |
| `scope=event` / `scope=attempt`, `duplicates_dropped` | Identical redeliveries dropped by each dedup stage |
| `lateness=lt_1m`, `1m_5m`, `5m_15m`, `15m_24h`, `too_late`, `attempts` | Processing time minus `attempted_at` for each new attempt, so configured and observed lateness can be compared |
| `reject_class=<class>`, `rejected` | Dead-lettered records per class: `undecodable`, `invalid_event`, `invalid_context`, `conflicting_duplicate` |

### Replay benchmark

[`fraud_streaming/benchmark.py`](../../src/data-pipeline/streaming/fraud_streaming/benchmark.py) replays a seeded workload with known shares through the job's own window, deduplication and horizon logic:
- late attempts (5–15 minutes);
- too-late attempts (beyond 24 hours);
- byte-identical duplicates (1.5%);
- conflicting copies.

It compares each variant with the v2 reference at hourly anchors:
- **handled:** the job's logic.
- **no dedup:** every delivery counts.
- **arrival time:** windows keyed on arrival instead of `attempted_at`.
- **baseline:** neither dedup nor attempt-time windows.

For each variant it reports mismatched cells, over- and under-counts, and the `too_late`, `duplicates_dropped`, `rejected` and lateness counters. The replay runs outside the Flink runtime; Flink itself is checked by the dev `stream-history` run.

Run: `cd src/data-pipeline/streaming && PYTHONPATH=.. uv run --locked python -m fraud_streaming.benchmark`.

Results with the module defaults: seed 2603, 1,200 attempts and 1,221 deliveries. CI pins these exact figures in `tests/test_benchmark.py`, so a change to the window or dedup logic that alters them fails the build. Injected: 58 late, 8 too late, 17 duplicates, 4 conflicting copies.

| Variant | Mismatched cells (of 3,234) | Over-count | Under-count |
|---|---|---|---|
| handled | 0 | 0 | 0 |
| no dedup | 541 | 850 | 0 |
| arrival time | 274 | 349 | 0 |
| baseline | 683 | 1,199 | 0 |

The handled variant's counters equal the injected workload: `too_late` 8, event `duplicates_dropped` 17, `rejected` (conflicting) 4, and lateness 5–15 minutes 58.

### Backpressure

The live job runs at 0% backpressure (see [Flink UI](#flink-ui)). The stress case is the history replay, which reads a seeded Kafka topic as fast as the job accepts it, so the pace is set by the slowest operator and everything upstream of it waits.

```mermaid
flowchart LR
    K["Seeded Kafka topic<br/>durable buffer"] --> S["Source + progress"]
    S --> D1["Deduplicate events"]
    D1 --> D2["Deduplicate attempts"]
    D2 --> C["Aggregate customer windows"]
    D2 --> M["Aggregate method windows"]
    C --> J["Feature journal<br/>exactly-once sink"]
    M --> J
    C -. "full input buffers<br/>(credit-based flow control)" .-> D2
    D2 -.-> D1
    D1 -.-> S
    S -. "stops polling" .-> K
```

Flink's flow control is credit-based: an operator whose input buffers are full stops granting credit to the one before it, so the pressure travels back to the Kafka source, which stops polling. Nothing is dropped and nothing grows without bound inside the job; the topic keeps the records. A checkpoint barrier travels with the data, so under backpressure it waits behind full buffers too.

#### Baseline: one operator sets the pace

One unit is one logical-clock job at parallelism 1, because replay needs a single ordered partition, so a unit cannot scale out. The baseline is a 7-day unit on a 3 GiB TaskManager with the JVM heap state backend.

![Backpressure in a history unit](images/online-replay-backpressure.png)

*Unit `20260819`, 2026-11-02 03:26 UTC (the UI shows UTC−5). The two aggregate operators are red at about 100% busy; the source and the first three operators are 90–99% backpressured and 1–8% busy.*

| Operator (REST `subtasks/metrics`) | Backpressured | Busy |
|---|---|---|
| Source | 96% | 4% |
| Observe source progress | 88% | 12% |
| Deduplicate events / attempts | 22% | 68% |
| Aggregate customer / method windows | 0% | 88% / 89% |

**Analysis.** `RUNNING` only proves the job is alive. The aggregate stage is the bottleneck: it takes about 75 records/s of input and spends about 12 ms on each one, while the source sits blocked. The source rate started near 1,150 events/s and settled near 350 events/s from about minute 10 as per-entity state grew. The TaskManager used 1.4–1.5 of its 2 CPUs, so the cost is the Python–JVM boundary and not a missing core.

![Checkpoints under backpressure](images/online-replay-checkpoints-before.png)

*Same job class: 25 checkpoints triggered in 11 min 45 s, 22 completed, 2 failed; the latest took 1 min 59 s at 148 MB. Unit `20261007` was restored twice with "Exceeded checkpoint tolerable failure threshold".*

With a 10 s interval and full heap snapshots, checkpoints ran close to the 2-minute timeout and some expired. An expired checkpoint fails the job, which restores from the last completed one.

#### Problems found and how each is handled

| Problem | Technique | Setting | Result |
|---|---|---|---|
| Checkpoints compete with the work under backpressure | Space them out and give them time; shrink in-flight buffers in front of a slow operator | `execution.checkpointing.min-pause: 2min`, `timeout: 10min`, `taskmanager.network.memory.buffer-debloat.enabled: true` | On the heap backend, one unit went from 25 checkpoints in 12 min with failures to 4 in 11 min, about 29 s each and no restores. The Kafka sink's 15-minute transaction timeout still covers a pause plus a checkpoint |
| Keyed state fills the heap | Keep state on disk, upload only what changed | `state.backend.type: rocksdb`, `execution.checkpointing.incremental: true`, TaskManager 5 GiB with managed memory split between RocksDB and the Python workers | At about 1M events a heap unit stood at 981 MB of 1,183 MB with repeated old-generation GCs, then heartbeats and checkpoints timed out and the job failed over to its last checkpoint, so committed offsets stopped moving; one TaskManager threw `OutOfMemoryError: Java heap space`. With RocksDB the same region passes with steady progress |
| One job cannot scale out | Scale across independent units | `historyUnitDays: 4`, `historyParallelism: 24`, two units per 4-vCPU burst node (TaskManager 1.4 CPU, JobManager 0.2 CPU) | 23 units replay at once instead of 14; each unit adds one lead-in day, so 4-day units do 25% extra work against 14% for 7-day ones |
| Slow Python state access | Larger Python-side state cache | `python.state.cache-size: 20000` (default 1,000) | Not measured separately from the other changes |
| Producer outruns the broker | Bound the producer's own buffer | The seed's `queue.buffering.max.kbytes`, one day per sort | The seed blocks on the broker instead of growing, so it stays inside its memory limit |
| Spot reclaim restarts a job | Do not let the autoscaler evict Flink pods | `karpenter.sh/do-not-disrupt` on the Flink pods | Karpenter had evicted JobManagers as "Underutilized" mid-run, restarting their jobs from the last checkpoint |
| A repeated seed costs a pass over Bronze | Reuse a finished seed | The seed report is keyed by unit and checked against the topic end offsets | A restarted run keeps the seeded topics and resets only the topics Flink writes |

Two attempts did not help. A 20,000-record Python bundle (default 1 s) made each Python stage finish a whole bundle before the next got input, so the stages stopped overlapping: busy time alternated between 100% and 0%, the source counter stayed flat for over 40 s and checkpoints took about 350 s. It was reverted. Rewriting the window state as incremental accumulators would not pay either: `Entity` already keeps running counts per window, expiry heaps and only the last 24 hours of attempts, and outside Flink one attempt costs 0.16 ms at 50,000 entities, 0.31 ms at 5,000 and 0.67 ms at 500, against about 12 ms per record in the job. Merging the two deduplication stages would remove one more boundary crossing, but they are keyed on different identities (`event_id` and the attempt) with separate conflict and counter semantics, so they stay apart.

#### After: RocksDB, 4-day units

![Backpressure on the source after the change](images/online-replay-backpressure-source.png)

*Unit `20260915`, 50 min into its run (02:49 in the UI, 07:49 UTC): the source subtask is 97% backpressured, 3% busy, status `HIGH`, while it still reads 803,000 records.*

![Backpressure on the customer aggregate after the change](images/online-replay-backpressure-aggregate.png)

*Same unit, `Aggregate customer windows`: 0% backpressured, 10% idle, 90% busy, status `OK`. This operator is the pacemaker; it is never blocked from below.*

![Checkpoints with RocksDB](images/online-replay-checkpoints-rocksdb.png)

*Same unit: 18 checkpoints triggered, 16 completed, 2 failed, none restored. Checkpoint 16 uploaded 255 MB of a 335 MB state and took 58.9 s.*

| Measure (unit `20260915`) | Baseline (heap, 7-day unit) | RocksDB, 4-day unit |
|---|---|---|
| Source / aggregate backpressured | 96% / 0% | 97% / 0% |
| Aggregate busy | 88–89% | 90–91% |
| Committed progress | stalls near 1M events, restoring in a loop | 363–383 events/s each at 2 units; 227–466 events/s across 6 units sampled with 14 running |
| Checkpoints | 22 of 25 completed, latest 1 min 59 s, 148 MB | 16 of 18 completed, average 46 s, longest 157 s |
| Checkpoint upload (average / largest) | full 148 MB | 85 / 255 MB, against 221 / 400 MB of full state |
| TaskManager | 1.4–1.5 of 2 CPU, heap 83% full (981 of 1,183 MB) | 1.3 of 1.4 CPU, 3.6 of 5 GiB |

**Analysis.** Backpressure itself did not move: the same operator is the bottleneck, so the per-unit rate stays near 350 events/s, and with 14 units sharing the pool it ranged from 227 to 466 events/s. What changed is that the job no longer fails over. The heap no longer fills and the checkpoint path completes, so progress is cumulative. RocksDB checkpoints are not shorter than the tuned heap ones (46 s on average against 29 s), because the bigger state is uploaded incrementally but still takes time; incremental checkpoints upload about 38% of the full state on average. The remaining lever is more units at once, which is limited by the 12-node, 48-vCPU burst pool.

**How to reproduce the UI evidence.** Port-forward `svc/fraud-streaming-history-v19-<YYYYMMDD>-rest` to `localhost:8081`, open the running job, select an operator, and choose **BackPressure** for the per-subtask percentage and status (`HIGH` above 90% backpressured, `OK` otherwise). Open **Checkpoints** for the counts, durations and the checkpointed against full size. The same busy and backpressured figures are available as `busyTimeMsPerSecond` and `backPressuredTimeMsPerSecond` at `/jobs/<id>/vertices/<id>/subtasks/metrics`, which is where the tables above come from.
