## Fraud serving design

The fraud runtime is an independently deployable Go module at `src/payment-gateway/fraud`; the Python rules service has been removed. It owns input validation and pure decision policy behind the existing `fraud.v1` internal gRPC boundary. A durable assessment coordinator owns fenced claims, bounded observations and immutable result replay. The optional Feast adapter retrieves independent customer/method observations in shadow mode; the model runtime remains pending. It uses the shared Go image and telemetry helpers without a compatibility wrapper or parallel implementation. Payments retains operational assessment errors for same-identity recovery and blocks processor effects until a valid assessment is committed.

Go Fraud uses Feast's supported feature-server API for bounded shadow retrieval. A later model adapter will call KServe directly and apply policy to its score. Feast's Python feature server owns SDK access and configured on-demand transformations; the predictor owns model execution and model-specific preprocessing. No custom Python coordinator between Go, Feast and KServe is required. Keep feature types, ordering, timestamps, freshness, missing-value behavior and model/feature versions explicit, and verify training/serving parity. Do not couple Go to Feast's internal Redis representation.

The streaming runtime in `src/data-pipeline/streaming` pins Flink/PyFlink 2.2.1, Java 17, Python 3.11.16 and Kafka SQL connector 5.0.0-2.2. Its optional `streaming.enabled` Helm resources use the platform operator in `operators`, Kubernetes HA and the dedicated `fraud-flink-prod` checkpoint/savepoint bucket. Credentials arrive from the application Doppler project through the feature chart’s ExternalSecret. A fresh live epoch starts at the current Kafka position and warms each history window; checkpoint recovery restores offsets and state. Historical replay starts at the beginning of an isolated source topic with its own logical clock and output epoch, using the existing immutable v16 source without regeneration. Snapshot `published_at` records the emission attempt, preceding checkpoint-coordinated Kafka visibility; it is not a broker commit or online availability timestamp. Runtime, checkpoint recovery and replay acceptance remain pending CI/deployed evidence.

The Feast 0.67.0 SDK writer and official server are defined in `src/data-pipeline/feast`; their Helm resources remain disabled pending streaming/replay acceptance. Two views store typed nullable quantities and protobuf snapshot metadata; keys hash length-prefixed UTF-8 epoch/view/integration/entity components. One ordered writer reads back accepted revisions before committing Kafka offsets. Registry files are generated in ephemeral memory; credentials arrive through ExternalSecret environment variables. KServe inference remains a later deployment. Python remains appropriate for training, Feast definitions/transformations and custom model runtimes. Knative is the planned serverless scaling option; verify the selected runtime's transport support, trace propagation, deadlines, cold starts and warm minimum replicas during that rollout. Use vendor HTTP or gRPC protocols behind adapters without adding a parallel internal business API.

Authoritative risk decisions and effect intents stay in the Payments transaction history. Send monitoring and prediction logging asynchronously from committed records, since an unavailable or awaited logging sink must never become a durable payment audit trail or an unconditional latency guarantee for the payment path itself.

## Shared feature semantics

The canonical [fraud-snapshot-v1 definition](../../contracts/features/fraud-snapshot-v1.yaml) and [conformance examples](../../contracts/features/fraud-snapshot-v1.examples.json) define three request quantities and seven assessed-history snapshot quantities. The pure Python reference in `src/data-pipeline/features/` has no Spark/Flink dependency; later native implementations must match its cases before claiming parity. Keys include integration identity, customer and method windows use independent snapshot anchors `[s-window,s)`, and a historical attempt contributes only after its start context and committed risk decision are available at the read cutoff. Declines count; the current attempt and undecided concurrent starts do not. Coverage is explicit per window; request-time elapsed seconds use the stored latest contributing start and become null outside the request-time seven-day horizon. Missing/stale history is not zero, missing IP is not shipping geography, and labels/scenario/oracle or future outcome fields never enter features.

Kafka/Flink continuously refresh history; Fraud never waits for the current attempt to traverse that pipeline. Historical replay using `recorded_at` is idealized and cannot reconstruct live pipeline lag. ML integration must retain actual served values or an immutable snapshot reference, cutoffs, freshness/missingness and feature/model/policy identities. Batch and online feature writers need independent progress and retry-safe versioned writes. Immediate 10s/60s submission observations remain separate from the ten model quantities and assessed-history snapshots.

## Training and drift

Training grain is one scored attempt/decision, not one payment event. Joins use scoped identity plus decision/attempt IDs; labels remain separate with `label_available_at`. Features use only information available at decision time, including ingestion/availability timestamps when events arrive late. Future outcomes, fraud truth and the decision itself must not leak into its features. Temporal evaluation splits, cold starts and late-label cases require explicit proof. Label cutoffs, chronological splits and dataset-version recording are all explicit and derived from the gateway's own dataset; maturity and warmup periods, keys and thresholds come from the gateway's own currency and scenario design, not from an external dataset's constants. The gateway training grain remains one attempt with strictly earlier features and labels available at its cutoff.

Training extends the accepted mini baseline: notebook acceptance requires that baseline, although exploration can overlap. Distributed training, incremental dataset storage, model registration and approved-model rollout to KServe (Knative and KServe serving) add capabilities without replacing mini generators, pipelines, windows or evidence. Training functions are shared between the notebook and pipeline, with orchestration kept thin on top of them. Drift compares versioned distributions without assuming immediate labels; retraining is deduplicated and cooldown-controlled, and promotion remains separately gated. See the [handoff checklist](../overview/roadmap.md#mini-to-final-handoff).

The prod-only Kubeflow Profile has GitOps configuration, not verified end-to-end ML workloads. Notebook v1 explores a fixed baseline; Kubeflow Pipelines coordinates the same training/evaluation stages through the shared Argo controller, with bounded Katib trials and Trainer for suitable multi-worker algorithms. DP1–DP3 retain direct Argo Workflows definitions and can use the shared Spark Operator when justified. KFP artifacts and logs use a separate RustFS bucket; curated Iceberg snapshots are the versioned training data. KFP's pinned Kubernetes-native build has no ML Metadata service, so persist explicit dataset snapshot, label cutoff, feature contract, source/image, Katib trial and pipeline run references with each candidate. The Profile's Hub Registry indexes immutable model artifacts and approved versions; KServe loads the approved URI and format, with promotion and rollback gated independently. The shared platform owns Kubeflow controllers, ingress and identity, while this repo owns the notebook, pipeline, registry client and serving contracts.

Use the existing Argo/Kubeflow platform, registry and GitHub Actions for orchestration, training and promotion rather than adding a separate Compose stack, Airflow, Jenkins, MLflow or another Kubernetes cluster.

The later [fraud investigation agent](../rag/fraud-investigation.md) reads recorded payment and fraud evidence; it never sits in the payment decision path.

## Development sequence

Use the new 90-day source for ingestion, feature and training development before scale generation. Build continuous Flink/Feast and Spark offline paths against the same pinned contract, then Kubeflow training/evaluation/registration and KServe serving. Full-scale Python generation and scale acceptance follow the exercised end-to-end path. A small source supports development but does not establish model quality; report warmup, mature label counts and chronological split limitations. Current rules-only Fraud has no deployed feature/model lookup or measured ML latency guarantee.
