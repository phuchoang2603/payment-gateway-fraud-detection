# Data generator

The historical generator writes immutable synthetic payment histories outside the operational payment database. The live adapter reuses a pinned historical entity world and sends commands to the gateway; it does not write directly to Fraud or payment storage. Source publication is separate from DP1 and DP2 acceptance. The mixed-schema implementation and its new development dataset remain pending acceptance.

## Configuration and identity

The maintained configuration is [`historical-smoke.yaml`](../../src/data-pipeline/simulator/configs/historical-smoke.yaml). It specifies 90 purchase-start days, seed 2603, US electronics calibration, entity pools, merchant/category Zipf skew, resource budgets and 2% extra duplicate deliveries relative to all exported event deliveries. Actual shares and duplicate rates are measured rather than guaranteed. Before any authorized run, select an unused `dataset_version` using `--dataset-version`; the placeholder is deliberately rejected. Never reuse or overwrite v16 or another completed version.

Stable seeds, integration identity, synthetic key version, entity pools, logical customer blocks, behavior, schema schedule, contracts and calibration identify the generated world. Worker counts, transfer concurrency, scratch limits and chunk size are execution controls. A changed logical input requires a new dataset version. Event completion and label availability may extend beyond the final purchase-start date.

## Schema definitions and schedule

[`physical-schemas-v1.yaml`](../../contracts/data-products/historical-payments/physical-schemas-v1.yaml) declares supported event and label shapes separately from supported event-envelope versions. The configuration selects an initial physical version and strictly increasing, timezone-aware effective times; each event uses its occurrence time, so a payment history can cross a boundary. Identical duplicate deliveries retain the original event and physical version. The first intended demonstration selects physical 3 and then 4 on 2025-08-15 UTC; the event envelope remains version 3.

Physical schema 3 has no assessment references; schema 4 adds optional references. Old absence normalizes to null. Synthetic references identify a deterministic representation of retained attempt signals and assessment values, not a persisted Fraud document or an online served feature vector; its serialization is specified by the source contract. Adding a later physical version requires its actual declared fields, supported Arrow types, source/Bronze contracts and direct lossless normalization. Preserve the earlier versioned schema-definition file and product/contract identities, publish a new definition file, and point the updated product and runtime to it; changing an existing definition would invalidate its recorded hash. Schedules select declared versions directly, including nonconsecutive versions; no intermediate data or pair-specific workflow is required. Unsupported shapes and ambiguous schedules fail before publication.

## Publication and recovery

After authorization and required CI checks, run the historical command with the selected configuration through the approved execution workflow. For a local destination, `simulator historical --config configs/historical-smoke.yaml --dataset-version <unused-version> --output <dir>` uses the same publication protocol. Remote credentials are supplied by the execution environment, not embedded in configuration. `--prepare-only` generates raw inventory without a completion manifest; a normal run continues the same generation identity. After a crash, stop the former writer before `--takeover-stopped-writer`; elapsed time alone never authorizes takeover. `--allow-small-dataset` is for bounded contract probes below one customer block.

The manifest is published last and pins configuration, generator and contract identities, schema definitions, exact inventory, hashes, row counts and physical/uncompressed bytes. Inventory paths are `raw/{table}/{task}/v{physical_schema_version}.parquet`; each file records per-date counts, using occurrence dates for events and availability dates for labels. Files are not guaranteed sorted or compacted. Completed manifests and raw objects are immutable. Compatible unfinished work resumes without rewriting completed files; cleanup deletes only `_run/` intermediates and retains a publication receipt. Failed cleanup is retried after integrity verification.

The source declaration defers quality validation to `dp1-starrocks-openmetadata`; publication is not Bronze acceptance. DP1 checks the selected files, persists duplicate deliveries, and validates independently pinned event and label snapshots. The historical RustFS probe established conditional create/update and streamed integrity checks; unsupported conditional operations fail instead of falling back to unsafe writes.

## Diagnostics and label meaning

Manifest counters distinguish configured entity pools from observed counts. Merchant/category shares use generated payment-created events; attempt missingness and risk counters use attempts; duplicate rate uses extra deliveries divided by all event deliveries. The [Spark diagnostic queries](../../src/data-pipeline/bronze-ingestion/data_platform/diagnostics.py) report observed scoped cardinality using `approx_count_distinct` and its relative error, decision-reference nulls and values by physical version and event date, and exact delivery accounting. A missing field in an older physical schema differs from an unavailable or invalid value in a schema that contains it. Diagnostic code and actual run output must be retained with the manifest hash; configured pools are not measured cardinalities.

Simulation truth and chargeback observations are distinct. Missing chargebacks are unknown, not negatives, and labels may only be used after `label_available_at`. Scenario, oracle truth, risk decisions and future outcomes are not predecision features. Use forward-time evaluation with mature labels and separate entity/campaign holdouts. Synthetic source distributions do not establish real-world model quality or full-scale acceptance.

The coursework source is `docs/coursework/rubic/EDAI K11 - DE.xlsx`, sheet `edai-1 (50%)`, cell B5; compression accounting is unspecified there. Full-scale evidence requires at least 100,000,000,000 physical bytes of inventory-listed event and label Parquet, excluding `_run`, reports, streaming data, replicas and downstream copies. The manifest separately records uncompressed column-chunk bytes and decimal GB/GiB, and a configured physical-byte gate prevents undersized publication. Development generation has no size minimum and is not evidence of that target.
