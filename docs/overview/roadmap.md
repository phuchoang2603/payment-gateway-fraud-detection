The tables describe planned capabilities and required proof for the gateway rework. All acceptance starts as **Planned**.

The adopted [gateway design](../payment-gateway/architecture.md#gateway-design) uses versioned payment/attempt rows, an append-only ledger and durable database idempotency. The first slice includes an isolated vault simulator and Redis-first idempotency claims/results with Postgres fallback, hosted checkout, Debezium publication and a signed-webhook notifier. Then prove a synthetic ISO 8583 bank exchange with a versioned profile and byte-level/recovery evidence. Separately introduce VND and issuer-authentication contracts from the [Vietnam policy research](../research/vietnam-payment-policy.md), then authorization/capture, journal and refunds. Add merchant-based Payments database sharding later, with directory routing, writer fencing, migration/rollback and per-shard CDC evidence. Automated reconciliation and bank settlement files are outside scope; keep status-based recovery. These are plans, not changes to current `payments.v1` or `fraud.v1` semantics. [Requirements](requirements.md) define delivery stages and acceptance goals.

The gateway implementation is in [`src/payment-gateway/`](../../src/payment-gateway), with [representative contract fixtures](../../contracts/payments/v1/testdata), [service integration tests](../../src/payment-gateway/payments/internal/application/service_test.go) and [prod manifests](../../infra/argocd/prod/root.yaml). Smoke and access acceptance run only on Kubernetes after GitOps rollout; the [verification evidence](../../openspec/changes/archive/2026-10-23-build-minimum-payment-gateway/verification.md) records the prod run and the [task checklist](../../openspec/changes/archive/2026-10-23-build-minimum-payment-gateway/tasks.md) retains two incomplete release-verification tasks for the minimum slice.

The rules runtime is an independently deployable Go service at `src/payment-gateway/fraud`, included in service logs, metrics and traces. Flink, the ordered Feast writer and official feature server are deployed; history remains shadow-only and velocity observe-only. The [streaming change](../../openspec/changes/archive/2026-10-28-build-streaming-fraud-features/tasks.md) records completed implementation and bounded acceptance. [Bounded live evidence](../../openspec/changes/archive/2026-10-28-build-streaming-fraud-features/evidence/live-rollout-2026-10-27.json) proves payment outcomes, evidence linkage and checkpoint recovery with a 2 GiB worker cap; Full v16 replay, sustained load and broad outage acceptance remain unverified and are outside this shadow/observe-only slice's acceptance. KServe and model rollout remain later ML work.

## Current implementation order

1. Finalize self-contained attempt events and the shared fraud feature contract; generate and exercise the new 90-day/10,000-customer development source and its current-time live landing. See [the change](../../openspec/changes/archive/2026-10-26-finalize-feature-contract-and-90-day-smoke/proposal.md). Source publication, live acceptance and downstream quality acceptance have separate evidence.
2. Build continuous Kafka/Flink assessed-history features and Feast online serving against the pinned definitions. Bounded state does not imply bounded input; Kafka remains unbounded.
3. Build/exercise Spark ingestion, curation, offline features and maturity-aware training datasets on the development source. DP1 historical and clean-landing development acceptance is complete; curation and offline features remain next.
4. Add Kubeflow training, evaluation and model registration, then KServe integration through Go Fraud with feature compatibility, latency/freshness and served-vector evidence.
5. Only after the end-to-end path is built and exercised, run full-scale Python generation and repeat scale/coursework acceptance. The 100 GB target remains required later; no Spark generator or legacy source compatibility is planned.

The six-day v13 acceptance remains historical evidence; old source versions are not current selectors. The operator stopped v14 and removed the old sources. V16 publication/source/live and DP1 historical/clean-landing development acceptance have separate evidence; feature, model and scale acceptance remain pending. Do not mark future engines or model quality complete from source generation alone.

## Planned data-platform direction

DP1 is deployed and development-accepted; DP2, DP3 and the feature/model stages remain targets. Immutable historical Parquet/manifests and completed Kafka landing batches feed Spark DP1 ingestion into RustFS-backed Iceberg bronze; DP2 curates silver, and DP3 produces reproducible features. Strimzi/Kafka remains the transport and Flink handles event-time streaming/checkpoints. Argo Workflows coordinates finite pipeline runs. **StarRocks is the selected shared SQL engine for data quality, analytics and gold data marts**, replacing the proposed Trino/analytical ClickHouse direction. The existing ClickHouse/HyperDX deployment remains for observability.

StarRocks queries the existing Iceberg REST catalog directly with native authentication; querying does not require copying the lake into internal tables or maintaining snapshot registrations. Native OpenMetadata discovery, profiling and SQL tests run under Argo from a thin image based on the matched official ingestion runtime. Its reusable Python SDK path owns governance synchronization and readback. GX, custom discovery/results and obsolete DP1-owned catalog artifacts have been removed; there is no legacy compatibility or migration path. Git contracts remain authoritative, and acceptance requires complete results tied to the selected source and Iceberg snapshots. The [DP1 plan](../../openspec/changes/archive/2026-10-27-historical-dp1-bronze/design.md) records implementation boundaries and completed native external-catalog verification; prior GX runs do not prove this path.

Gold uses explicit **fact/dimension star-schema marts** with declared grain, keys, join cardinalities and SCD2 effective-time semantics. Prefer StarRocks SQL over curated Iceberg inputs; materialize selected joins/aggregates where measurements justify it rather than requiring pre-flattened OBTs or a full warehouse copy. SCD2 history and point-in-time joins remain explicit transformations, not automatic consequences of a star schema. Immutable lake snapshots remain the reproducible training source; moving gold views do not replace versioned feature/label inputs.

DP2 planning consumes accepted DP1 snapshot pairs and completion-ledger versions. Silver curation deduplicates business identities while preserving raw delivery provenance, reconstructs complete lifecycle context and enforces the SQL in `contracts/quality/silver-payments.yaml`. Late labels remain independent inputs; training targets use availability and maturity boundaries. Initial gold grains are one payment attempt (`fact_payment_attempt`), one observed chargeback (`fact_chargeback`) and merchant/customer context versions (`dim_merchant`, `dim_customer`). Keys include integration scope; SCD2 dimensions use nonoverlapping `[valid_from_ts, valid_to_ts)` intervals and facts join as of attempt occurrence. Version source snapshots, late corrections and refresh completion; select materialized views only after fixed-query correctness and resource comparisons. These are planning boundaries, not implemented marts or benchmark results.

**Automated gold materialized views** use StarRocks native refresh facilities. Views over external Iceberg tables support scheduled or explicit refresh, not immediate refresh triggered by every Iceberg commit. Argo can trigger and await refresh after upstream acceptance; record upstream versions, refresh completion, freshness/lag and failure recovery before exposing accepted gold. Materialized views store derived data and consume refresh compute/storage. Optional later native StarRocks serving loads require a measured latency need. Demonstrate late-data correction, SCD2 changes and equal query results before claiming real-time or performance improvements.

The platform repo owns StarRocks and its official Kubernetes operator/Helm deployment under Argo CD; this repo owns SQL, contracts, mart/refresh definitions and native OpenMetadata workflows. Start with measured on-prem Spark/Flink/StarRocks baselines and lake maintenance. Reuse existing CI jobs and focused behavioral checks; avoid configuration-only suites and redundant tests. Later optional AWS Spark bursting uses immutable staged snapshots, cloud-local output and bounded import, subject to measured correctness, recovery, transfer cost and capacity; it is not the default execution path.

## ML extension

Final ML extends the accepted baseline. Training acceptance depends on baseline acceptance; exploratory work may overlap. Preserve baseline assets and rerun their regressions.

Prefer Kubeflow Pipelines for fraud-model training, evaluation and artifact handoffs; use Kubeflow's other ML components only when they serve a concrete need. The shared platform owns their installation, while this repository owns its pipeline definitions and model contracts. Kubeflow Pipelines uses Argo Workflows by default, but its v2 pipeline format is engine-independent. Keep direct Argo Workflows for DP1–DP3 Spark/StarRocks and native OpenMetadata orchestration rather than duplicating those data pipelines.

The prod-only `fraud-ml-prod` Profile and its Hub Registry, KFP launcher, artifact configuration and Doppler-backed secrets now have GitOps manifests ([deployment guide](../deployment/gitops.md)); the shared platform owns Dex, the Dashboard/Profiles, Notebook v1, KFP, Katib, Trainer, KServe/Knative, Hub, Spark Operator and the single Argo Workflows controller. This is infrastructure configuration, **not** proof of working ML runs, authenticated access or model serving. Do not install a second stack on dev. The platform's Kubernetes-native KFP build is experimental and has no ML Metadata service: demonstrate actual runs and artifact/log round trips, and record run, model, code and Iceberg snapshot IDs explicitly instead of assuming automatic lineage. See the platform's [Kubeflow operations guide](https://github.com/phuchoang2603/talos-proxmox/blob/main/docs/operations/kubeflow.md) and [platform rollout #23](https://github.com/phuchoang2603/talos-proxmox/issues/23).

Use Notebook v1 for the reproducible training baseline, then package the same pinned feature contract, image and temporal split as a KFP pipeline. Run bounded Katib trials over that baseline; use Trainer for genuine multi-worker training when the chosen algorithm supports it, or record why another distributed runtime meets the requirement. Persist immutable weights and pipeline artifacts in owned object storage, register model/version/artifact metadata in the Profile's Hub Registry, and keep incremental training datasets in governed lake snapshots rather than treating the registry or the KFP artifact bucket as a dataset version-control system. An approved registry version supplies the immutable artifact URI and model format for the KServe `InferenceService`; promotion and rollback remain explicit gates. Use Spark Operator only when it improves DP1–DP3 job lifecycle; Hub Catalog is optional for external model discovery, not a dependency of a locally trained fraud classifier. Notebook, Katib, Trainer, registry and KServe integration each require their own evidence, not merely a Dashboard link.

The selected ML serving boundary is Go fraud calling Feast's feature server and KServe's predictor directly. Feast retains Python SDK/on-demand transformation execution; Python is also used for training and custom model runtimes where needed. There is no required custom Python feature/decision coordinator. Version feature freshness/missing-value semantics and model inputs, prove offline/online parity, and validate Knative scaling and cold-start/deadline behavior separately from the Go replacement.

## Deferred decisions and limits

- Versioned payment events and fraud RPC schemas exist under [`contracts/`](../../contracts). The minimum gateway implements configured integration identities, checkout and attempt APIs; [verification evidence and rollout prerequisites](../deployment/gitops.md#gateway-verification) distinguish local checks from outstanding production acceptance.
- Synthetic processing comes first. Real card custody, live processor connectivity, wallets, seller payouts, FX and PCI certification are outside this baseline.
- Availability and fraud quality require measured evidence. There is no five-nines or real-world model-quality claim.
- Fraud is internal-only gRPC on port 8000 with named health probes; the chart creates no public ingress. The Go edge owns HTTP/JSON translation. Gateway exposure and routing policy remain with routing, service access and secrets.
- Model traffic experiments record the authoritative model per decision. Shadow inference cannot execute payment effects. Application canary delivery is related but does not itself prove model A/B evaluation.

## Acceptance and evidence

- Record the implementation revision, artifact/data versions, environment/resources, commands, expected and observed results, and failure/retry cases. Keep new results alongside their workload docs, with explained images and links to available machine-readable reports.
- Retain unoptimized measurements, fixed inputs and resource settings for comparisons. Measure improvements and runtime acceptance on the new implementation.
- Document deployable units, external boundaries and numbered data flows; schemas across all zones, naming, SCD2 and feature timestamps; module/function responsibilities; and five implemented ML classes with their interfaces and collaborators.
- CI/CD requires tests, builds and automatic deployment for every listed workload, even when templates are shared. Go gateway services and coordinated contract changes are additional CI/CD obligations; the Python fraud replacement requires no legacy runtime compatibility. Image builds run in CI; secrets stay outside code.
- Course tools illustrate capabilities. Explain equivalent implementations and their proof. Grouping rubric requirements is allowed; row IDs, point accounting and rubric snapshots are unnecessary. Preserve required thresholds, lineage and versioned evidence.
- Synthetic model quality does not establish real-world fraud performance. Unlabelled drift measures distribution changes, not prediction accuracy. Full gateway, training, rollout and load acceptance remain separate from the scoped service checks.
