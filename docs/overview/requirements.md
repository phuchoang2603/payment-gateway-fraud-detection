# Requirements

These requirements describe the planned system, not delivered behavior. **First slice** means the API-driven synthetic gateway in the [minimum gateway plan](../../openspec/changes/archive/2026-10-23-build-minimum-payment-gateway/design.md); **later** means a separate implementation increment.

## Functional requirements

| ID | Requirement | Delivery / acceptance |
| --- | --- | --- |
| FR-01 | Authenticate configured integrations and derive integration-scoped merchant/customer UUIDv5 identities in Payments. | First slice; reject cross-integration access; one full-snapshot payment request needs no provisioning call. |
| FR-02 | Create immutable amount/currency/order snapshots, scoped checkout sessions and idempotent attempts; expose authenticated payment status. | First slice; repeated requests return their stored result and changed content conflicts. Hosted checkout supports decline-then-retry in the first slice. |
| FR-03 | Run an isolated vault simulator that tokenizes allow-listed fictional card fixtures into opaque, integration-scoped tokens. Only the vault owns its token mappings and encrypted fixture records. | First slice; Edge tokenizes allow-listed test cards through the hosted form or synthetic-only API and obtains safe method metadata, and only the processor identity can resolve processing fixtures. Reject real card fields and foreign tokens. |
| FR-04 | Request a versioned fraud decision and record it before any processor effect. | First slice; fraud errors fail closed and no processor request follows a risk decline. |
| FR-05 | Execute simulated sales through a provider adapter with a durable effect intent and operation key. | First slice; demonstrate success, processor decline and a lost response without duplicate processing. |
| FR-06 | Recover uncertain operations by querying the simulator and expire only payments without unresolved effects. | First slice; crash/restart converges on one recorded result. Unresolved cases stay pending; no bank-file reconciliation worker is included. |
| FR-07 | Use Redis first for atomic in-flight idempotency claims and completed results for creation and attempts, with request binding, TTL and noeviction. | First slice; cache miss, memory exhaustion, restart and outage fall back to durable database behavior without another charge. |
| FR-08 | Publish committed events through WAL CDC/Kafka and deliver signed, deduplicated merchant webhooks with bounded retries. | First slice; broker/webhook outages do not block committing payment outcomes. |
| FR-09 | Transmit and parse a named synthetic ISO 8583 bank profile behind the provider adapter. | Later; byte fixtures, framing, correlation, duplicates, late responses and safe uncertainty handling. Live bank connectivity is outside this synthetic scope. |
| FR-10 | Add VND and issuer-authentication scenarios using versioned regulatory, provider and synthetic policy sources. | Later; update contracts, units, lifecycle and generators together; do not reinterpret existing USD or APPROVE/DECLINE semantics. |
| FR-11 | Add separate authorization/capture and refund commands with a balanced journal and captured-amount limits. | Later; replay never repeats a financial effect, and cumulative refunds cannot exceed captured funds. |
| FR-12 | Feed reproducible data/feature pipelines, approved model serving and read-only fraud investigation from scoped committed evidence. | Later; preserve temporal cutoffs, delayed-label separation and independent sink progress. See [data pipeline architecture](../data-ml/data-pipeline.md). |

Automated reconciliation, bank settlement-file ingestion, settlement verification, real card custody, live money movement, payouts and FX are outside the revised project scope. Operation-status recovery remains necessary even in simulation; processor success is not a claim of bank settlement.

Current data development uses self-contained attempt context and a shared versioned feature definition, proven on a 90-day small source before scale generation. [Roadmap](roadmap.md#current-implementation-order) orders Flink/Feast, Spark offline processing and Kubeflow/KServe work. This development source does not fulfill the later 100 GB scale target or establish production model quality.

## Non-functional requirements

The numerical targets below are initial acceptance goals for the synthetic gateway. Record hardware, dataset, configured simulator latency and injected faults with each run; no target is an observed result or a PCI certification claim.

| ID | Requirement | Acceptance target / evidence |
| --- | --- | --- |
| NFR-01 | Durable, strongly consistent payment commands. | Each transition commits versioned state, exactly one append-only ledger event and idempotency atomically with expected row versions. Concurrent retries and repeated recovery produce zero additional processor effects in the acceptance suite. Acknowledged writes survive application restart. |
| NFR-02 | Bounded checkout latency and explicit uncertainty. | Under nominal synthetic load, target p95 attempt response <= 1 s at 50 attempts/s for 10 minutes, with < 0.1% unexpected transport/5xx errors. Risk/processor declines are business outcomes; `assessment_status: ASSESSMENT_ERROR` is an operational failure. Fault runs are reported separately; use a 1 s fraud deadline, 3 s processor deadline and 5 s overall attempt budget, returning pending on an uncertain processor result. |
| NFR-03 | Availability with bounded dependency failures. | Initial deployed API objective: 99.9% monthly valid-request availability, counting unexpected 5xx/timeouts, operational assessment failures and database/vault failures; measure at Edge with a declared probe/window. Redis outage must preserve payment correctness via database fallback. A short smoke test cannot establish the monthly SLO. |
| NFR-04 | Credential isolation and tenant authorization. | Use authenticated, encrypted service transport and least-privilege roles/network policy. Vault is a separate deployable and database owner; other application roles cannot read its tables, and only the processor identity may receive processing fixtures through its API. Encrypt stored fictional fixture payloads with a vault-only key from External Secrets. Keep tokens, raw card fields and fixture payloads out of logs/events/Fraud/Redis/lake. This demonstrates a PCI DSS-oriented boundary using synthetic data, not compliance. |
| NFR-05 | Safe recovery and delivery. | After a one-replica restart or injected lost processor response, resolve known simulator outcomes within 30 s once dependencies return under the stated test load. Never turn unknown into decline solely because time elapsed. CDC/webhook delivery is at least once with stable identities and exponential backoff/jitter. |
| NFR-06 | Horizontal growth and later database sharding. | Start with one Payments database and stateless service replicas. Later use a versioned shard directory keyed by `(integration_id, merchant_id)`; colocate each payment's state, events, idempotency and future journal. Prove routing, tenant isolation, hot-merchant handling, migration/rollback and per-shard CDC before enabling multiple shards. Redis partitioning is a separate decision. |
| NFR-07 | Traceable operations without sensitive payloads. | Propagate correlation IDs and per-payment event versions and record policy/model/feature versions. Acceptance captures request rates, p95/p99 latency, failures, pending age, cache hit/error rates and vault authorization failures. Add export/dashboards as their telemetry increment lands. |
| NFR-08 | Reproducible, independently deployable services. | Keep domain code free of transport/storage dependencies, version shared contracts, test real persistence boundaries, build per-service images and render the prod GitOps target. Commands read current state; direct lifecycle tests and ledger integration checks validate transitions without reactivating processor effects. |

Database sharding (NFR-06) is an explicit later scaling increment, not part of the first deployment; see [later database sharding](../payment-gateway/payment-flows.md#later-database-sharding). The initial availability objective is NFR-03.
