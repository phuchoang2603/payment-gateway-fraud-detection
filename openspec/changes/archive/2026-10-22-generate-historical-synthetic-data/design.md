## Context

Main has an ODCS v3.1.0 agreement (`contracts/data/historical-payments.odcs.yaml`) with schemas and DuckDB SQL quality rules for payment events and labels, an ODPS v1.1.0 descriptor (`contracts/products/historical-payments.odps.yaml`), a generated schema reference, and a CI job that lints both with pinned Data Contract CLI 1.2.7 and Data Product CLI 0.3.2. There is no generator. Object storage is the existing MinIO on TrueNAS at `minio.home.phuchoang.sbs`, outside the Talos clusters and Argo CD. The old generator followed the [fraud detection handbook](https://fraud-detection-handbook.github.io/fraud-detection-handbook/Chapter_3_GettingStarted/SimulatedDataset.html) with card-present terminals that `payments.v1` cannot represent.

ODPS describes the product as a whole (owner, access, ports). ODCS describes the promise behind each port (schema, quality). Validation is two steps: lint the YAML, then run the contract's quality rules against real data.

## Goals / Non-Goals

**Goals:**

- One folder per data product, holding its descriptor and its contracts.
- One command that reproduces a dataset from config and seed, with rubric-visible data problems.
- One set of rules: the ODCS SQL checks gate publication and are reused by ingesting jobs.

**Non-Goals:**

- Live generation, Kafka and transport faults (`simulate-live-traffic-with-transport-faults`).
- Golden protobuf lifecycle histories (`build-minimum-payment-gateway`).
- Container images, Helm charts, Argo Workflows or Kubernetes jobs for the generator. It is a finite, seeded batch run from a workstation; DP1 decides later how ingestion is scheduled.
- DataHub and Spark/Flink rule execution.
- Writing the source as an Iceberg table. The RustFS S3 Tables Iceberg REST catalog is for DP1's bronze layer.
- Bronze tables, analytical schemas (#45), features, configurable drift (#44).

## Decisions

### Product folder layout

```
contracts/
  payments/v1/ labels/v1/ fraud/v2/      # protobuf wire contracts (unchanged)
  synthetic/identity-vectors.json
  data-products/
    historical-payments/
      product.odps.yaml                  # ODPS: id, owner, ports, access
      payment-events.odcs.yaml           # ODCS: payment_events schema + lifecycle rules
      fraud-labels.odcs.yaml             # ODCS: fraud_labels schema + label rules
docs/data-ml/
  data-products.md                       # how products work, historical section, evidence
  data-products/historical-payments/
    payment-events.md                    # generated by datacontract export
    fraud-labels.md                      # generated by datacontract export
```

`contracts/` stays the single cross-language contract boundary. A future product adds a sibling folder; CI discovers `contracts/data-products/*/product.odps.yaml` and `*.odcs.yaml` so no workflow edit is needed. Rejected: root `data-products/` (splits shared contracts across two roots) and placing contracts inside `src/simulator` (couples a shared agreement to one producer).

### Two ports, two contracts

| Port | Contract | Purpose |
|---|---|---|
| `payment-events` | `urn:datacontract:fraud:historical-payment-events` | Lifecycle events, read by DP1 as model inputs |
| `fraud-labels` | `urn:datacontract:fraud:historical-fraud-labels` | Delayed chargebacks and simulation truth, joined only after `label_available_at` |

Labels and events have different consumers and leakage risk, so each gets its own promise and version. The existing rules move unchanged except for one: `label_attempt_linkage` still queries the `payment_events` table, so `fraud-labels` declares the events contract in `inputContracts` and its validation runs against a database holding both tables. Both contracts keep the shared owner, `classification: synthetic` and `sqlDialect: duckdb`. Product version becomes 2.0.0; both contracts start at 1.0.0 under new IDs because the old ID is retired rather than reused with a different shape.

### Generator writes the ODCS shape directly

Records are built as Arrow tables using a schema declared in the simulator that mirrors the ODCS fields: typed envelope columns, one struct column per lifecycle payload, `timestamp[us, UTC]`, enum names as strings. A simulator test reads each ODCS file and checks the Arrow schema has the same column names and nullability, so drift fails CI. Rejected: protobuf-first with a descriptor-driven mapper (a second schema source and code to maintain) and a Python lifecycle validator (duplicates the ODCS SQL rules).

### Publication gated by native validation

Per run: generate per day-chunk → flush raw Parquet to a local staging directory → write the final sorted files locally (see Parquet layout) → create DuckDB views `payment_events` and `fraud_labels` over the final files with `hive_partitioning = false`, so the partition key does not show up as an undeclared column → run `datacontract test` for both contracts → only on pass, upload files and reports to the dataset prefix and write `manifest.json` last. Validation runs on exactly the bytes that get published. A failure aborts with the CLI report and no manifest. The CLI is invoked as a pinned subprocess through `uvx`, the same command documented for ingesting jobs.

### Output layout

```
s3://synthetic-source/historical/<dataset_version>/
  payment_events/occurred_date=YYYY-MM-DD/part-NNNNN.parquet
  fraud_labels/label_available_date=YYYY-MM-DD/part-NNNNN.parquet
  validation/{payment-events,fraud-labels}.json
  manifest.json
```

The manifest records config and its hash, seed, generator revision, product ID and version, each contract ID, version and file hash, row counts per partition, storage settings with per-table file, row-group and byte counts, data-problem statistics, history end, profile digest and synthetic key version. Existing manifests are never overwritten.

### Parquet layout

Final files come from one DuckDB `COPY (SELECT … ORDER BY …) TO … (FORMAT parquet, …)` per partition, run with a memory limit and a spill directory. That gives an external sort, row-group sizing and file rotation in one engine call, replacing the hand-written `ParquetWriter` rotation loop of the earlier implementation. A local check with DuckDB 1.4 on 3M synthetic rows produced zstd files near a 32 MB target, 131,072-row row groups with timestamp min/max statistics, `timestamp[us, UTC]`, dictionary encoding on low-cardinality strings and plain encoding on hashes. The sort ran under a 256 MiB cap in 14 s.

- **Partitioning: daily, compacted.** A day is DP1's incremental unit, matches the generator's and live simulator's day loop, and lets labels be read by availability day. Each day is written as one sorted file, split only past `target_file_mb`. Full event days target at least about 1 MB; sparse label partitions and the final event tail are accepted below that target, preserving daily boundaries without padding. Events partition by `occurred_at`; labels by `label_available_at`.
- **Sorting:** events by `occurred_at, payment_id, aggregate_version, event_id`; labels by `label_available_at, payment_id, attempt_id, source`. Time filters skip row groups, and a payment's events sit together. Duplicate exports are sorted in beside their originals, so no file holds only duplicates.
- **Sizes:** `storage.row_group_rows` (default 131,072) and `storage.target_file_mb` (default 128) are separate settings. Files rotate at a row-group boundary, so the target is approximate. DuckDB applies the row-group size in multiples of its 2,048-row vector, so smaller values have no effect. Small days stay small; files are never padded or merged across partitions. Defaults are re-checked against the first real run's manifest metrics.
- **Encoding and compression:** zstd level 3, DuckDB's automatic per-chunk dictionary choice, and statistics on. Delta encoding and bloom filters are not configured: nothing reads by point lookup yet, and any benefit must first be measured on real output. The notebook reports compressed bytes per column from Parquet metadata, so encoding changes are made from evidence.
- **Schema cutover:** each day is entirely before or after `cutover_date`, so each partition has exactly one physical schema.

### Iceberg comes later, in bronze

RustFS 1.0 provides S3 Tables with an Iceberg REST catalog, but table maintenance (`rewrite_manifests`, `rewrite_data_files`) was still being fixed through 1.0.3. The source stays plain Parquet with a manifest: it is an immutable input whose version is the dataset version, and ODCS validation reads exactly the published bytes. DP1 appends a dataset version into a bronze Iceberg table in a RustFS table bucket, with hidden partitioning such as `days(occurred_at)`, and owns compaction and snapshots there. The source layout (sorted, zstd, `timestamp[us, UTC]`, explicit schema versions) keeps that load a straight append.

### Default volume

`configs/historical.yaml` covers 90 days: long enough for 30-day customer baselines, chargeback delays of up to three weeks to land inside the window, several non-overlapping compromise windows per scenario, and a schema cutover with enough days on both sides. Customer count is set so a run finishes in minutes on a workstation.

### Fraud scenarios

| Scenario | Shape | History signal |
|---|---|---|
| `obvious_high_value` | Amount far above category price | Single-attempt sanity check |
| `stolen_card_new_device` | Compromised customer, new device and IP, elevated amounts, time-bounded window | New device/IP, amount vs 30-day average |
| `card_testing` | Low-amount bursts, many method fingerprints, shared device, high declines | Declines and distinct methods per device per hour |
| `account_takeover` | Old account, new device, foreign IP, new shipping address, high-value categories | IP country ≠ shipping country, account age, new address |
| `friendly_fraud` | Legitimate attempts later charged back | Label noise only |

Each is enabled and parameterized independently. A day-by-day loop selects compromised entities per day, as in the handbook. Device farms, reshipping mules and retry attacks are left for later configs.

### Decisions and processor outcomes

The generator applies its own small policy recorded as `sim-rules-v1`; it does not import or call the fraud service. Processor declines, insufficient funds and unknown outcomes that later resolve are simulated in-process with configured rates. Training uses labels, not these decisions.

### Data problems

- Skew: Zipf exponents for merchant popularity and category mix.
- High cardinality: configured distinct fingerprint counts, plus one-off fingerprints from fraud.
- Schema evolution: before `cutover_date`, partitions omit `attempt_started.signals.user_agent_family` and use `schema_version` 1; from it on, version 2. The ODCS `sinceSchemaVersion` metadata already describes this.
- Duplicates: a seeded sample of events is exported again with identical content and sorted in beside the original. The ODCS rules already accept identical repeats and reject conflicting ones.

### Continuity with live simulation

Random streams are `SeedSequence(seed, stage)` for profiles and `SeedSequence(seed, stage, day, chunk)` per day-chunk, so any day's schedule can be rebuilt without replaying earlier days and output does not depend on processing order. Entity IDs are pre-assigned from profile indexes, and generation works on integer entity codes, mapping them to string IDs only when building Arrow batches. Parallel workers are added only if the first timing run needs them; chunk-keyed streams make that possible without changing output. Merchant and customer IDs are UUIDv5 of the synthetic `integration_id` and external IDs; fingerprints are HMAC-SHA256 under the non-secret synthetic key; both are checked against `contracts/synthetic/identity-vectors.json`. The manifest's profile digest lets the live simulator refuse a mismatched rebuild. Profiles are not written as a dataset because they carry raw synthetic addresses and compromise truth.

### Local execution

The generator is a uv-managed CLI run from the devenv shell, for example `doppler run -- uv run simulator historical --config configs/historical.yaml --output s3://synthetic-source`. A run needs only network access to MinIO and the pinned `datacontract` CLI, and the result is fully determined by config, seed and revision, so there is nothing to schedule, retry or observe in-cluster. Both reference repos run their generators this way and keep orchestrators for downstream jobs. Rejected: the earlier prod Argo Workflow, Helm chart and image, which added a release pipeline, a data namespace and cluster secrets for a one-off batch. If volume ever outgrows a workstation, the same CLI can be wrapped by DP1's orchestrator without changing output.

### Storage and libraries

Files are staged and validated locally, then uploaded with `pyarrow.fs.S3FileSystem` (`endpoint_override`, path-style addressing, `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` from the environment via Doppler `prd` or a gitignored `.env`). `--output` accepts `s3://…` or a local path. Libraries: numpy (PCG64), pyarrow, duckdb, pydantic, PyYAML; notebook group adds matplotlib and Jupyter.

## Risks / Trade-offs

- [Scenarios too easy or impossible] → Check fraud rate and distributions in the notebook, tune, bump `dataset_version`.
- [Arrow schema drifts from ODCS] → The schema parity test.
- [Splitting contracts breaks cross-table rule] → Labels validation always runs with both views; the input contract makes the dependency explicit.
- [DuckDB-only SQL] → Spark/Flink support is verified with those pipelines, not assumed.
- [Validating large datasets locally is slow] → Default config sized for minutes; validation runs once per dataset.
- [Local disk holds staging, final files and sort spill at once] → Each day's raw staging files are deleted after its final files are written; the manifest records stored bytes so disk needs are known before scaling up.
- [Small daily files at low volume] → One compacted file per day, and the first run's manifest metrics decide whether the default volume needs raising.
- [NAS availability] → Local output keeps tests and CI independent.

## Migration Plan

1. Move and split the contracts, regenerate references, update CI and docs in the same commit; old paths are deleted, not aliased.
2. Land the generator and tests.
3. Generate a new dataset version, run the notebook and record evidence.
4. After the new version is accepted, delete superseded `historical/*` prefixes produced under the old contract. No consumer reads them yet.

Rollback: revert the commit; delete the new dataset prefix.
